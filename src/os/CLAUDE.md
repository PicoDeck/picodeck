# OS core (`src/os/`)

Subsystem notes for the launcher, app runners, Lua bridge, sandbox and OS services. The root `CLAUDE.md` holds the summary and the cross-cutting rules.

## App runners (`launcher.c`, `app_runner.h`)
- The launcher reads `app.json` with a hand-rolled minimal JSON parser (no cJSON, for flash) and dispatches through the `AppRunner` vtable.
- **Lua** (`lua_runner.c`): allocates a 64 KB VM stack, reads `main.lua`, then runs the whole VM lifetime on that stack (PSP): fresh `lua_State`, `lua_bridge_register()`, `lua_pcall()`, error screen, `lua_close()`.
- **Native** (`native_loader.c`): ELF32 PIE loader, relocates to PSRAM (code in SRAM if it fits), runs on the PSP. All header/segment/dynamic/relocation validation is in `elf_plan.c` (pure; shared with the simulator's `unicorn_runner.c`, host-tested in `tests/unit/test_elf_plan.c`, fuzzed by `tests/fuzz/fuzz_elf_plan.c`). Only `R_ARM_RELATIVE` is applied; `R_ARM_ABS32/GLOB_DAT/JUMP_SLOT` (undefined weak symbols in newlib's unwinder) are bounds-checked and left as-is; any other relocation type rejects the app.
- **Hidden apps** (`launcher.c`, `app_manifest.c`, `mv_op.c`): `/apps/.test` (the E2E harness's, wiped freely) and `/apps/.dev` (the user's own) are dot-named, so `on_app_dir` skips them: never in the table, the menu or `MAX_APPS`. Only the dev `launch` (`launcher_launch_by_name`, so `launch_app` and the simulator's `launch_app` RPC) reaches them. `launch <name>` tries every listed match first (id, display name, directory: a listed app of the same name wins), then the hidden roots; `launch .test/<name>` and `launch .dev/<name>` search only that root (no listed app can shadow it: the harness and the MCP `launch_app(hidden=)` use this form for what they staged, and the harness fails if the reply does not say `from /apps/.test`). The whole argument is at most 69 characters (`.test/` + a 63-character name); a longer one is refused ("app name too long"), never truncated into a different app. `hidden_find` takes a name `app_hidden_name_valid` accepts (1-63 characters, no `/`, `\`, control characters or `..`, no leading or trailing `.`; anything else is "not found"), tries the directory name in each root (`.test`, then `.dev`), then lists them for an `app.json` id (case-insensitive), quietly (no per-candidate warnings). Both the scan and this lookup build the `app_entry_t` with `app_entry_load` (main.lua/main.elf check, `path`, `app_manifest_parse`, icon only for the scan), and the run goes through `run_app_entry` (identity, sandbox, `running.txt`, outcome, teardown as for a listed app; `APP_DIR` is `/apps/.test/<name>`, data `/data/<id>`; the log says `Starting hidden app <path>`). The entry is not allocated per launch: `s_apps` has `EXTRA_SLOTS` (2) entries after the `MAX_APPS` listed ones, `HIDDEN_SLOT` for the app being run (read by the simulator's RPC thread through `s_running_app_name`, so it must outlive the run) and `LIST_SLOT` for `list all`'s scratch (the simulator serves `list all` mid-app); no static SRAM. The manifest is read fresh at every launch, and the reply is `[DEV] Launching app from /apps/.test: <arg> (<name>)`. Nothing in the launcher UI or the app-facing API reaches them. `list all` prints them in a `Hidden apps:` section, tagged `[.test]` / `[.dev]`, before a `Total: N apps, M hidden` line (host tools end the reply at `Total:`).
- **`mv <src> <dst>`** (`dev_op_mv` → `mv_op.c`, `mv_path.c`, `drivers/fat_within.c`; `tests/unit/test_mv_op.c` runs it on the vendored FatFS over a RAM disk, FAT and exFAT): FatFS reads far more than the spelling it is given (`\` is a separator, `//` collapses, `.` components, a trailing dot or space is stripped, a long name also matches its 8.3 alias) and `f_rename` does not check for a subtree (a directory renamed below itself is cut out of the tree), so a string comparison proves nothing. Both paths are first reduced to one canonical form (`mv_path_canon`: absolute, `\` mapped, repeated and trailing `/` dropped; a `.`/`..` component, a name ending in `.` or space, a control character or `"*:<>?|` is "bad path"); `/`, `/apps`, `/data` and `/system` are never moved or moved onto. Then three questions are asked by FatFS identity, `sdcard_path_within(root, path)` (under the SD mutex: open `root` and every ancestor of `path`, compare the directories' first clusters, whatever the spelling): is the source or the target (or an ancestor of it) `/system`; is the target inside the source directory; does the source hold the running app's directory (`app_identity_current()`). Each also has a string-prefix guard on the canonical paths that needs no FatFS call. **The identity test fails closed**: FatFS opens a directory through its 16-entry open-file table (shared by every open file: a Lua app can hold 32 tracked files, Core 1's stream one more), so with the table full `f_opendir` fails for a directory that exists while `f_rename` still works; only `FR_NO_FILE`/`FR_NO_PATH` means "not inside", any other failure is `SDCARD_WITHIN_UNKNOWN` and `mv` refuses ("cannot verify the move (too many open files?): close files and retry"). An existing target (case-only renames included: FatFS refuses those) is refused; missing parents of the target are created, and removed again if the rename fails (a target deeper than 8 new levels is refused). The simulator's `sdcard_path_within` compares device and inode.
- **Identity** (`app_identity.c`): both runners first install the app's identity (id, `/apps/<dir>`, `/data/<id>`, requirement flags and the full requirement list, held in PSRAM) and clear it after teardown; for Lua this happens before `lua_bridge_register()`. Every enforcement check reads it through `app_identity_current()` / `app_identity_has_requirement(name)`, never the `APP_*` Lua globals.
- **Stacks** (`app_stack.c`): `app_stack_run()` paints the stack, arms `PSPLIM` above a 32-byte guard (overflow = STKOF HardFault, crash record names `PSP (Lua VM)` / `PSP (native app)`), switches Thread mode to the PSP, calls the runtime, switches back. One runner is active at a time, so there is one PSP user; IRQs always use the MSP. The launcher itself stays on the MSP; its dev commands and screenshot save use `app_stack_run_os()` (32 KB PSRAM, owner `PSP (OS command)`), which runs inline when an app stack is already active, so `app_stack_run` never nests. The `stack` dev command reports the last launcher command's peak (`os_cmd_peak`, ~5.3 KB for a 66-file unzip).
- **Exit teardown.**
  - Launcher, around every app: full-screen clip rect, scroll offset 0, font 0 and `font_registry_unload_all()`, `perf_init()` (the `setTargetFPS` target, pacing deadline and frame history, so a native app never inherits a Lua app's pacing), `system_menu_clear_items()`, `zip_archive_close_all()`.
  - Lua runner: `lua_close()` (every userdata `__gc`), then leftover files (`app_files_close_all`), tone/stream stop, `fileplayer_reset`, `sound_init`, `mp3_player_reset`; Core 1 is resumed before `lua_close` if the app left it paused (`sys.pauseBackground`); REPL scrollback freed. Keyboard state is cleared at launch (`kbd_clear_state`), as in the native loader.
  - Native runner: every object the app got through the API is tracked against it — files in `app_files_*`, images/samples/sample players/file players/MP3 players/video players/MOD players/terminals/AES and ECDH contexts/`qmiAlloc` blocks in `app_res_*` (`app_identity.h`, kinds in `native_loader.h`). After the app returns the loader frees whatever is left (`native_res_release_all`), does the same audio resets, `http_close_all`/`tcp_close_all` (while Core 1 runs), clears the audio callback and drops a latched `reboot-ota`. Firmware tracks through a per-launch PSRAM copy of `g_api` whose create/free entries adopt/drop the handle (same layout; every other entry is `g_api`'s); the simulator's Unicorn trampolines call the same `native_res_adopt`/`native_res_drop`/`native_file_*`. A free of an untracked pointer is ignored (see the stale-free caveat under App Model in the root file).

## Lua bridge internals (`lua_bridge*.c`)
- One file per `picocalc.*` module, coordinated by `lua_bridge.c`. Non-obvious placements: `picocalc.game` spans `lua_bridge_game*.c` (camera, scene, save); `lua_bridge_appconfig.c` registers both `picocalc.config` and `picocalc.appconfig`; `lua_bridge_3d.c` defines the global `draw3DWireframeEx`; `picocalc.network` HTTP connections use the `HTTP_MT` metatable.
- **Object types**: every userdata type registers with `lb_register_type(L, mtname, methods, meta)`: methods live in a separate `__index` table, the metatable holds only metamethods (`__gc`, `__close`, custom `__index`/`__newindex` functions, which get the methods table as upvalue 1) and is locked with `__metatable = false`, so `obj:__gc()` is "attempt to call a nil value". A finaliser can hand an object to a method after the object's own `__gc` ran (resurrection), so each `__gc` leaves its object dead (pointer NULLed or a `destroyed` flag). Graphics, terminal, video, modplayer and the sound types then raise from `check_*`; the handle types (fs file, zip archive, tcp, http, crypto) treat a finalised handle as closed: `close` and some getters accept it, and I/O raises. `picocalc.modplayer.create()` returns the one live handle for the single MOD player. `display.getBackBuffer()` is the one **stateless** type: a singleton full userdata built in `lua_bridge_display_init()` (`display_register_fb`) and handed back by every call. It carries no pointer — it refers to the back buffer *by role*, so it stays valid across the `flush()` swap, like `display.setPixel`/`getPixel` — and exposes only bulk `getPixels`/`setPixels` (no single-pixel mirror, which `display.getPixel` already is). `fb:getPixels/setPixels` validate the rectangle against the screen (w/h bounded before the byte count is multiplied) before allocating, so a huge request raises `outside the screen`, never out-of-memory; `setPixels` returns false only for an on-screen rectangle wholly outside the clip rect.
- **Volume root and zip indexes**: `fs.exists/stat/isDir("/")` are answered in `lua_bridge_fs.c` (`path_is_root`: a directory of size 0) because FatFS `f_stat` refuses the root while the simulator's host `stat()` accepts it; `sdcard_stat` itself is left alone so `deleteRecursive("/")` stays refused on firmware. Zip entry indexes are 0-based, as in the C API, and exact integers (a fractional index raises); `zip_reader_extract_entry` rejects an out-of-range index (`no such entry`) before `extract_streamed` opens the destination "w", so a bad index never truncates an existing file.
- **Argument types**: check userdata with `luaL_checkudata`/`luaL_testudata`. Image arguments go through `lb_check_image`, and draw paths that keep an image pointer (sprite `setSourceRect`, spritesheet `drawFrame`, animation loop `draw`) refuse freed pixels. Only documented types are accepted: `image.loadFromBuffer` takes a string or a `qmibuf` handle (length checked against its size); `sprite.new` takes an image or nothing.
- **Graphics object lifetimes** (`lua_bridge_graphics.c`): every C pointer from one graphics object to another is anchored in a user value (`anchor_set`): a sprite keeps its image, stencil and tilemap, a spritesheet its image, a tilemap its tileset, an animation loop its frames. The display list (`s_sprites[]`) is mirrored by a registry table, so an `add()`ed sprite is never collected while displayed; `remove()`/`removeSprites()`/`removeAll()` release it; `add()` is idempotent. Enumeration (`getAllSprites`, `performOnAllSprites`, `query*`, `overlappingSprites`, `moveWithCollisions`) and `getImage()` return the real objects. Blinkers are held weakly by `updateAll`. Sprite `width`/`height` are bounds only; drawing and `alphaCollision` use the image's (or source rect's) own size.
- **gfx3d** (`lua_bridge_gfx3d.c` over the pure `gfx3d.c`, host-tested in `tests/unit/test_gfx3d.c`): one context per app, created on first use and freed by `lua_close` (a registry userdata, `picocalc.gfx3d.context`); `draw*` transform, cull, light and clip at once and store only screen-space records, so no mesh pointer outlives the call; sprite images are anchored in a registry table until the next `beginScene`. The rasteriser (`disp_fill_tri_f`, top-left rule, bit-identical shared edges) and span fill live in `display_clip.h`; `gfx3d.c` builds with `-ffp-contract=off` on every target. Perf (device, 200 MHz, 804 tris submitted): draw ≈ 8.0 ms, endScene ≈ 4.8 ms, 16.5 ms median per frame including the Lua loop and service passes. Follow-ups: profile per phase (with `xip_cache_hit_rate`, and without harness polling) — geometry costs ~10 µs/triangle, likely PSRAM/XIP-bound; hoist the per-edge slope divisions out of `disp_fill_tri_f`'s row loop; reserve all fan records up front so a near-clipped quad is never half-drawn at overflow.
- **Compile-time config**: `cmake/picodeck_lua.cmake` (`PICODECK_LUA_DEFINITIONS`, applied `PUBLIC` by the firmware and simulator builds): `LUA_32BITS=1`, `LUA_USE_LONGJMP=1`, `LUAI_MAXSTACK=1000`, `LUAI_MAXCCALLS=60`, `LUA_IDSIZE=60`. Upstream `luaconf.h` hard-codes these (`LUAI_MAXCCALLS` is already guarded in `llimits.h`), so the same file patches it (`#if !defined` guards, idempotent, marker comment on line 1) at CMake configure time, from `make download-lua`, and in the CI workflows. `_Static_assert`s in `lua_bridge.c` fail the build if the patch is lost.
- **Numbers**: `lua_Integer` is 32-bit (wraps at ±2^31; hex literals like `0xDEADBEEF` wrap to negative, `%x` still prints the 32-bit pattern); `lua_Number` is `float` (~7 significant digits, integers exact only to 2^24, `1e39 == math.huge`). `sys.getTimeMs()` goes negative after ~24.8 days uptime (differences still wrap correctly); `getClock().epoch` overflows in 2038; file sizes above 2 GB read negative.
- **Float formatting** (`tostring`, `..`, `string.format` `%a/%e/%f/%g`, JSON, REPL) goes through `lua_numfmt.c` on both targets, never the C library (`luaconf.h`'s `l_sprintf` is patched to `picodeck_lua_sprintf`): output matches glibc exactly (`tostring(51.0)` is `"51.0"` on device too), except NaN always prints `nan`. Subnormals (<1.2e-38) print `0.0` on the device because the RP2350 flushes them when a float is promoted to double.
- **Quantity arguments** (coordinates, sizes, durations, volumes, rates, frame indices; `lb_checkint`/`lb_optint`) round floats to nearest (ties toward +inf), so `199.99998` draws at 200 and `fillRect(10.5, …)` and `img:draw(10.5, …)` both land on x = 11; NaN/inf and floats beyond ±2^24 are argument errors. Narrow sinks clamp instead of wrapping (`lb_clamp_int`): volumes, `rgb` components, effect factors and brightness to their documented range, unsigned times/positions at 0. Identifiers (handles, enums, colours, masks, byte counts, ports) require exact integers.
- **`LUAI_MAXSTACK`** counts stack *slots*, not frames: a typical frame costs 10–13 slots, so recursion tops out around 80–100 levels; the smallest frames cost ~1 slot, so unbounded recursion of them reaches ~976 levels before its `"stack overflow"` (why the service hook's arming must not walk the frames, below). 1000 is the smallest value that ran every app in the tree (500 overflowed the minesweeper flood fill).
- **`LUAI_MAXCCALLS=60`** caps nested C calls and parser levels. Lua→C→Lua recursion (e.g. nested `string.gsub` callbacks, ~864 bytes of C stack per level on device) stops at ~58 levels with a catchable `"C stack overflow"` error, before the 64 KB VM stack runs out (measured peak 51.4 KB). Raise it only together with `LUA_VM_STACK_SIZE` in `lua_runner.c`.
- **Service hook** (`lua_bridge.c`): with any count hook installed, Lua 5.4 runs `luaG_traceexec` before *every* instruction, whatever the count (P0 measured it as ~60% of VM time on the device). So on firmware the VM runs **hook-free**: a 1 ms Core 0 repeating timer (`lua_bridge_arm_cb`, default alarm pool; the period counts from the end of each callback, so a late or slow one never re-fires back to back) arms a count-1 hook on the running thread with `picodeck_lua_arm_hook` (`lua_hook_arm.c`, built into the Lua library through `PICODECK_LUA_SOURCES` because it uses VM internals; host-tested against the real Lua core in `tests/unit/test_lua_hook_arm.c`), and `menu_lua_hook` disarms it and runs `lua_bridge_service_poll()`. `picodeck_lua_arm_hook` makes `lua_sethook`'s stores (async-safe, `lua.c`'s SIGINT pattern) but sets the trap of only the innermost Lua frame, so it costs the same at any depth; a return across a C boundary into an untrapped outer frame waits for the next tick. Never arm with `lua_sethook` from the timer: it traps every frame on the chain, and ~1000 frames deep (unbounded recursion of small frames) that walk of QMI PSRAM outlasted the 1 ms period, the then fixed-rate timer re-fired inside its own IRQ forever, and the watchdog reset the device (issue #21). The timer itself is started once, at the first Lua app (`lua_bridge_hook_start`), and then runs for the rest of the boot; it only arms the hook when `s_async_active` is true (an app's VM is running), so it is a no-op between apps and at the launcher. If no alarm slot is free at that first registration, firmware falls back to the synchronous count hook instead (logged: `[LUA] no alarm slot for the service timer: synchronous hook`). The running thread is whatever `lua_corolib.c` (our fork of `lcorolib.c`) last reported through `lua_bridge_set_running()`: every resume, the return from it, and the `__close` handlers run by `coroutine.close`/a failed `coroutine.wrap`. The simulator and the web build (no Core 0 interrupt) keep the synchronous count hook, which adapts between 128 and 4096 instructions to fire about once per ms; so does every VM between `lua_bridge_exit_reset(L)` and `lua_close` (its `__gc` handlers). Every service call feeds the watchdog and checks the exit request and the Sym (Menu) key (`kbd_consume_menu_press()`); the full pass (HTTP/TCP/sound callbacks, the serial dev-command poll, reboot flags, screenshots, low-memory GC) runs only when `g_lua_service_pending` is set (Core 1's sound trampolines, the simulator's control socket; `lua_bridge_request_service()`) or 5 ms have passed since the last one. `input.update()` and `display.flush`/`flushRows`/`flushRegion` run the same gated pass; `sys.sleep` (every 10 ms, after a `kbd_poll_background()` that queues keys without consuming the app's edges) and the terminal widget's blocking waits run the full pass (`lua_bridge_service()`).
- **App exit is sticky.** `sys.exit()`, the system menu's Exit App and the dev `exit` command (`exit_app`) all call `lua_bridge_raise_exit()`: it sets an exit flag the Lua runner owns (and the dev exit flag, so modal loops unwind), raises the exit sentinel, and installs a count-1 hook with `lua_sethook`, which traps every Lua frame on the chain, on the raising thread at every raise (even over a timer-armed hook, which traps only the innermost frame) and on the main thread at the first raise or whenever its hook is not armed (both hook modes). A `pcall`/`xpcall`/`coroutine.resume`/callback `lua_pcall` that swallows the sentinel cannot keep the app alive: the next instruction outside it raises again. The runner clears the flag after the app's `pcall` returns (before `lua_close`), and an app that exits by rethrowing some other error gets the exit outcome, not the error screen.

## Sandbox, files and per-app stores
- **Signature verifiers** (`crypto_rsa_verify`, `crypto_ecdsa_p256_verify` in `crypto.c`): the SSH wire blobs (RSA key, ECDSA key, ECDSA `mpint(r)+mpint(s)` signature) are parsed by the pure `ssh_blob.c`, whose every length is checked as `len > (uint32_t)(end - p - 4)`: never `p + len > end`, which wraps on the 32-bit target. `test_ssh_blob` (parsers, crafted blobs) and `test_crypto_verify` (crypto.c over the host mbedTLS, `cmake/mbedtls_host_config.h`) cover them; a 64-bit host can't wrap the pointer, so the wrap cases only fail the old check under `-m32`. Hash must be exactly 32 bytes (the bridge raises); an RSA signature must be exactly the modulus length.
- **Sandbox** (`fs_sandbox_check` → `fs_path_allowed` in `fs_path.c`, host-tested): without `"root-filesystem"`, reads of the app's own `/apps/<dir>` and of `/system/lib/`, read + write of `/data/<app_id>`; relative paths and any `..` are refused. It guards `picocalc.fs.*`, the image, font and zip loaders, the sound loaders (`sound.sample`/`sampleplayer` paths, `sample:load`, `sample:save`, `fileplayer:load`, `mp3player:load`), `modplayer:load`, `video:load`, `crypto.sha256File` and `require` (app dir, then `/system/lib`). `"root-filesystem"` bypasses it. `fs.browse(start)` checks `start` for read access and falls back to the app's data root.
- **File handles** (`lua_bridge_fs.c`): `picocalc.fs.open(path [, mode])` returns a full userdata (metatable `picocalc.fs.file`, hidden) or `nil, err`. `fs.read(h, n)` and `h:read(n)` are the same function (likewise `write`/`close`/`seek`/`tell`). A closed handle raises "attempt to use a closed file"; `close` is idempotent and `fs.close(nil)` is a no-op; any other value (a string, a light userdata, another module's userdata) is a type error. `read` rejects a negative length and clamps to the bytes left; it and `readFile` read straight into a Lua buffer, so `readFile` of a file larger than free memory raises a memory error (it does not return `nil`). A dropped handle is closed by `__gc`, `local f <close> = fs.open(...)` closes at scope exit, and every open file is on the running app's open-file list (`app_files_*` in `app_identity.h`), which `lua_run` sweeps after `lua_close` — FatFS allows only 16 open files (`FF_FS_LOCK`), so a leak would otherwise break `f_open` until a reboot.
- **Per-app config** (`picocalc.config` / `g_api.appconfig`): always the running app's own `/data/<app_id>/config.json`; the store is bound to the identity's id on each call and unbound at every app start and exit. Native `load(id)` binds only the app's own id (`app_config_load_own`, case-insensitive); another id is refused and leaves the binding unchanged.
- **System config** (`config.c`, `/system/config.json`, flat JSON, `config_load()` at boot, `config_save()` writes back): Lua `picocalc.sysconfig.get/set/save/load` is registered only with the `"sysconfig"` requirement (otherwise nil). `wifi_pass` is write-only through that API (`get` returns nil); the file itself stays readable by any native app and any `root-filesystem` Lua app. Native apps have no system-config API. Well-known keys: `wifi_ssid`, `wifi_pass`, `brightness`, `dim_timeout_s` (idle dim in seconds; `"0"` disables; default 60), `tz_offset`, `dev_mode`, `wifi_auto_disconnect`, `battery_pct`, `show_fps` (`"tr"`/`"tl"`/`"br"`/`"bl"`; Off is no key, `"0"` also reads as Off), `bt_enabled` (`"1"`: Bluetooth controllers on, read at boot; Off is no key), plus the editor's `editor_font` and the store's `store_url` override. Keys and values share one `CONFIG_POOL_SIZE` (1024 B) static-SRAM pool of `key\0value\0` pairs (was 10 fixed 160-byte slots, 1600 B, which those keys filled exactly), so capacity is in bytes: every documented key at its longest (a 127-char `store_url`, a 63-char password) takes ~400 B. Keys are cut to 31 chars and values to 127 at `config_set` and at load, as before; a new key, or a longer value, that does not fit is dropped silently (the old value stays), a pair that does not fit at load is dropped with a log line, and a key repeated in the file keeps its last copy (as in JSON), so the pool holds each key once. `config_get` pointers are valid until the next `config_set`/`config_load` (they move the pool); every caller uses them at once.
- **Gamepad bindings** (`gamepad_map.c`, `gamepad.c`): `/system/gamepad.json` (the global map over the defaults; a separate file, so the bindings don't compete for the system config's 1 KB pool) and `/data/<app_id>/gamepad.json` (one app's override: only the buttons it lists, the rest from the global map; a key it uses leaves the inherited buttons). Human-editable `{"a":["F4"],"up":["Up","W"],"x":[]}` read by a small reader over `flat_json_read_string`, written through `sd_atomic_write` (`gamepad_save`, which creates `/data/<id>`); files over 2 KB, corrupt or missing mean the defaults / no override, never a failed launch; unknown button and key names are skipped and logged (`[GAMEPAD]`). Key names come from the one table in `gamepad_map.c` (also `getLabel` and the Settings page); `gamepad_map_bind` is the one-button-per-key rule (reports where the key moved from). Both runners call `gamepad_apply()` right after installing the identity: it builds the effective map on an OS stack (`app_stack_run_os`, 32 KB PSRAM from the launcher) and installs it with `kbd_set_pad_map`. Host-tested in `tests/unit/test_gamepad_map.c`. The map covers keys only: pad sources (`src/drivers/pad_source.h`: the `pad` dev command, the simulator's controller, a Bluetooth pad) report `PAD_*` directly and are ORed in by the keyboard driver (`src/drivers/CLAUDE.md`, Pad sources); the launcher and system menu read their presses as navigation (`kbd_get_pad_nav_pressed`) and `ui.c` draws the header's pad icon.
- **Settings → Controls** (`system_menu.c` draws it over the pure `gamepad_edit.c`; `tests/unit/test_gamepad_edit.c`, `tests/e2e/test_controls.py`): the global map at the launcher; in a game, This game (the override, the default; buttons it does not list are drawn dimmed, lighter on the selection bar) or All games. Capture reads `kbd_poll_event` keycodes (so letters bind) and ignores the Enter that started it and any key's own repeats (arrows, Enter and letters repeat as fresh PRESSED items, not HOLD); a key `gamepad_key_bindable` rejects is refused by name and capture goes on, except Shift, Alt and Sym, passed over quietly (the menu key is Shift+F5; Shift and F5 in one keyboard scan can report F5 first, which then binds); the menu key (`kbd_consume_menu_press`) cancels; Esc binds; Brk is left to take its screenshot after the menu closes. In This game a slot bound or cleared on an inherited button, or a key moved off one, makes that button an override. Leaving saves (`gamepad_save`/`gamepad_remove`): the global file lists only the buttons that differ from the defaults, the override its buttons, either removed when empty; then `gamepad_apply`. A file that is there but unreadable (`gamepad_load_file` → `GAMEPAD_FILE_UNREADABLE`) keeps the page shut, so the defaults are never saved over it; a corrupt one (`IGNORED`) opens as the defaults, as launches read it. The page first wants an 8 KB PSRAM block (`CTL_HEAP_MIN`): the SD layer's `f_stat` allocates, and a failed allocation there reads as a missing file. Out of memory (that, the state, the launcher's 32 KB OS stack) shows "Not enough memory for Controls". Stack: the menu also runs on the launcher's 4 KB MSP, so the state is one `umm_malloc`'d `gamepad_edit_t`, the file work runs on `app_stack_run_os`, and the page (inlined into `menu_loop`: 280 B before it, 288 with it, 304 with the menu's screen restore) adds ~210 B at its deepest draw chain; no static SRAM.
- **App ids** are a path component (`/data/<id>`): 1-79 characters of `[A-Za-z0-9._-]`, no `..`, no trailing `.` (FatFS strips it, so `com.victim.` would alias `/data/com.victim`); folded to lower case (FatFS is case-insensitive) and the sandbox compares paths case-insensitively. The launcher refuses an invalid id (on-screen reason + `/system/error.log`, as for `min_psram_kb`). A missing `id` defaults to `local.<dir>` with any other character (and a trailing `.`) replaced by `_`. The scan warns when two ids fold to the same value (they would share `/data/<id>`). The SD card auto-creates `/data/` and `/system/` on first mount.

## Save slots (`picocalc.game.save`, `lua_bridge_game_save.c`)
- Each slot is `/data/<app_id>/saves/<name>.json` (directory created on first use); the id comes from the C-owned identity. Serialised with the shared JSON encoder/decoder (`lua_json_encode_push` / `lua_json_decode_push` in `lua_bridge_json.c`); whole floats are written with `.0` so `math.type` survives a round trip (`picocalc.json` too).
- Names must pass `fs_name_valid` (`fs_path.c`): 1–128 bytes of `[A-Za-z0-9._-]`, no `..`, no leading `.`. Anything else: `set` returns `false, "invalid save name"`, `get` nil, `exists`/`delete` false.
- Legacy migration: the old shared `/saves/<name>.json` is never modified or removed. When an app **reads** (`get`/`exists`) a name it has no slot for and the legacy file exists, the file is **copied** into its slot; `set`/`delete` never copy. A marker `saves/.migrated-<name>` (written on the copy, or when `set`/`delete` touch a name that has a legacy file) stops a later `delete` from being undone by a fresh copy; markers start with `.` so `list()` never shows them. `list()` shows only the app's own slots.

## System update (`sys.applyUpdate`, `ota_verify.c`)
`sys.applyUpdate(path)` is registered only when the app declares `"system-update"` AND is an OS app: id `net.picodeck.updater` or `net.picodeck.store`, or a directory under `/system/`. That allow-list is **self-declared** (any app can claim an OS id in its own `app.json`); it narrows the API, it is not the boundary. The real controls are the signature, the confirm and the boot token:
- **Signature.** An image is flashed only if `/system/update.sig` (DER ECDSA P-256 over SHA-256 of the image, as `openssl dgst -sha256 -sign` writes) verifies against the public key embedded in the running firmware (`ota_verify.c`, shared verbatim with the simulator and `tests/unit/test_ota_verify.c`). `/system/update.sha256` (strict: exactly 64 hex digits + optional newline) is still required but only a cheap pre-check. `applyUpdate` checks sandbox → size/vector table → checksum → signature before its dialog; the boot re-checks checksum + signature over the exact bytes it is about to write (PSRAM copy).
- **Confirm.** `applyUpdate` shows a `ui_confirm` naming the file; declining returns `false, "cancelled"`. `ui_confirm` discards input queued before it appears (STM32 FIFO, injected keys), ignores input for 400 ms, and needs a fresh Enter press edge (or `y`), so an app cannot pre-load a "yes".
- **Boot token.** The boot applies an update only with the one-shot OTA token (`OTA_MAGIC` in watchdog scratch[1], set only by C in `ota_trigger_update` — after the confirm, or by the `reboot-ota` dev command). A `/system/update.bin` found without the token is renamed to `update.bin.stale` (with its `.sha256`/`.sig`) and logged. An image the boot refuses (bad checksum/signature, too big, OOM…) is renamed to `update.bin.rejected` (+ `.sha256`/`.sig`), the reason is shown and logged as `OTA REJECTED` in `/system/error.log`, and it is never retried. The HardFault record also uses scratch[1] (stacked PC), so `main()` zeroes it on the crash path.
- **Keys.** The embedded key comes from the CMake option `PICODECK_UPDATE_PUBKEY_PEM`, default `tests/keys/picodeck-update-TEST-public.pem` — a TEST key whose private half is in the repo, so dev builds accept anything signed with it and `make flash-ota` signs with it (`tools/ota_flash.py --key`, or `make flash-ota OTA_KEY=<priv.pem>`). `.github/workflows/release.yml` refuses to build without the `UPDATE_SIGNING_KEY` secret (a P-256 private key PEM): it embeds that key's public half (`-DPICODECK_REQUIRE_RELEASE_UPDATE_KEY=ON` rejects the test key) and publishes `picodeck.sig` next to `.bin`/`.sha256`. `tools/sign_update.py sign|verify|genkey` wraps the openssl CLI. Firmware built with one key only accepts images signed by that key — changing keys needs one UF2 flash (or an OTA signed with the OLD key).
- The store and updater fetch `picodeck.sha256` and `picodeck.sig` from the release; the store refuses to download an image when either is missing.

## Error and crash records (`crashlog.c`, `src/main.c`)
- `/system/error.log` — app-level failures written while the OS is alive (Lua runtime errors and panics, native loader errors, launch refusals); every entry ends with a `Heap:` line (free / largest block / fragmentation).
- `/system/crashlog.txt` — OS-level records written at boot: HardFault dumps decoded from watchdog scratch (with the app name) and `UNCLEAN EXIT` entries when an app hung until the watchdog fired.
- HardFault record (`hardfault_c`; layout in the comment above `CRASH_TAG` in `src/main.c`): the SDK's `watchdog_reboot(0,0,0)` zeroes scratch[4], so what must survive is in scratch[0-3]; scratch[1] doubles as the OTA token outside a record. After a stacking-time STKOF the stacked PC/LR can be garbage. The fault screen is held ~3 s, then the device reboots.
- `/system/running.txt` — dirty-exit marker written at launch and deleted when the runner returns. If it survives to the next boot the app never came back to the launcher; the boot names it on screen for hardfault/watchdog cases (a plain power-off mid-app also leaves it and is only echoed to serial). Intentional reboots (system menu, `sys.reboot`, dev `reboot`) clear it first.
- `sys.getMemInfo()` returns `psram_largest_block` and `psram_fragmentation` alongside the totals, plus the small-object pool figures below.

## Lua heap (`lua_psram_alloc.c`, `small_alloc.c`)
- umm blocks are 200 bytes (`UMM_BLOCK_BODY_SIZE`) because block indices are 15-bit: 6,160,384 / 200 = 30,801 blocks, and the smallest 8-aligned size that stays under 32,768 is 192. Every umm allocation costs at least one block.
- `lua_psram_alloc` puts requests of up to 128 B in `small_alloc.c` size-class pools (16-128 B, 4,196-byte slabs of 21 umm blocks); larger ones are umm blocks. Slabs are umm blocks, so `psram_free`/`psram_largest_block`/`psram_fragmentation` still describe the whole heap. The pools are created by a VM's first small request and their slabs go back to umm at `lua_close`; inside an app a slab is returned only when its last object dies, so one surviving object pins its 4 KB slab and `psram_largest_block` can sit well below `psram_free` mid-app. `sys.getMemInfo()` reports `small_pool_slabs`, `small_pool_bytes`, `small_pool_objects`, `small_pool_object_bytes`. `-DPICODECK_LUA_SMALL_POOLS=0` builds without them.
- Lua `sys.qmiPsramAlloc(size)` returns a bounds-checked buffer handle (userdata owning a `umm_malloc` block, freed by `qmiPsramFree` or GC); `qmiPsramRead/Write(handle, offset, …)` raise on out-of-range or freed handles. No raw pointers reach Lua.

## OS overlay (`os_overlay.c`, `fps_counter.c`)
- `os_overlay_draw(kind, y0, y1)` runs just before every app present: Lua `display.flush`/`flushRows`/`flushRegion` (`lua_bridge_display.c`), the native `g_api.display` wrappers (`src/main.c`) and the simulator's native trampolines. The launcher and the system menu call `display_flush()` directly, so nothing is drawn there. It advances the toast queue and draws the toast, then the Show FPS counter, in font 0 with a full-screen clip (the app's font and clip are restored).
- **Partial presents**: an overlay is drawn only into the rows being sent (clip rect = the band). One that reaches outside them is composed and pushed with `display_push_rect` when its id (toast expiry time; FPS value, colour and corner) or rectangle changes: save the app's pixels under it (`umm_malloc`, ≤ 9 KB for a full-width toast), draw, push, restore. So the app's draw buffer keeps its own pixels there, and an overlay that goes away or moves is erased by pushing the buffer's rectangle. `s_shown` records what the panel shows. An overlay inside the rows stays in the buffer, as with `flush()`, so an erase push is clean only where no earlier present sent the overlay's rows: an app that repaints only dirty bands keeps a stale toast/box there after expiry or a corner change (as it would after `flush()`). With a non-zero hardware-scroll offset nothing is drawn: a partial present pushes the buffer's rows back over every shown rectangle (which removes a composed box from frame memory; one drawn into the app's buffer, such as panels' full-screen `flushRows` just before it starts scrolling, is part of its ring image and scrolls away with it) and forgets `s_shown`, so the overlays come back once the offset is 0. The system menu calls `os_overlay_reload()` when it closes (re-read `show_fps`, forget `s_shown`), since it drew over them, after giving the app its screen back and before an app item's callback (which may flush, or leave by longjmp). It draws nothing: the restored front shows the overlays as the app's last present left them (a `flush()` app's box at the old corner and value; a `flushRows` app's pushed box is in no buffer) and the new setting shows from the next present (`test_show_fps.py::test_new_corner_shows_at_the_next_present_after_the_menu`). A repaint on close was left out: the pixels under a box drawn into a `flush()` frame are gone, so the old box cannot be erased (pushing the back buffer's rectangle would show another frame, often with an older box), a second box at the new corner would show two counters, and the value read over the menu's pause is wrong (its first window after the menu spans the pause, so it reads low for a second, as it did before the restore). Other OS modals (file browser, `ui_confirm`, text input) do not, so a composed overlay is re-pushed only when it changes after them.
- **Counting** (`fps_counter.c`, pure, `tests/unit/test_fps_counter.c`): rates over windows of ≥ 1 s (events after the opening one, per second of span, rounded); presents (flush/flushRegion = 1; `flushRows` counts only a new sweep, `y0` ≤ the previous call's, and only with no flush/flushRegion in the last second), and `perf_end_frame` ticks, which win while one came in the last 2 s. `os_overlay_app_start()` (launcher, before every app) zeroes it and re-reads `show_fps`; the system menu's Settings item writes the key (or removes it for Off) and the menu's close reloads it. Static SRAM: 52 B of BSS (`s_fps` 28, `s_shown` 24; `s_fps_mode` fits in padding).

## System menu (`system_menu.c`)
- **The app's screen comes back.** `menu_loop` saves both framebuffers (`display_save_buffers`, into a 400 KB `umm_malloc` block held only while the menu is open) before `display_darken()`, and on every way out of the loop restores them in their roles (`display_restore_buffers`) and frees the block, next to `bg_free()`. So a dirty-rect app (or one waiting for a key) needs no repaint. Not at the launcher (context 0), which redraws itself after the menu. The copy is the extra: the menu's own 200 KB backdrop (`bg_alloc`) is allocated first, then the copy, which is freed again at once if the largest free block is then under `CTL_HEAP_MIN` (the Controls page's own test, so umm's 200-byte block rounding and a second free block count exactly as they will there; the freed copy merges back, leaving the heap as it was). So on any heap the menu keeps its backdrop and the Controls page whenever it did before the copy existed (`tests/e2e/test_menu_memory.py` walks it on the real umm, `--real-umm`, from 4 KB to 700 KB free, including the 622,700 B rounding boundary). Without the room (a nearly full or fragmented heap, C-Dogs for one) nothing is saved and the menu closes over the darkened screen, as before. The hardware-scroll offset is reset at entry and not restored (the panels contract, `display_get_scroll_offset_writes`).
- **The menu key toggles the menu.** `menu_loop` takes `kbd_consume_menu_press()` every pass: the menu key (Shift+F5 / F10 on the keyboard, or a pad's Home, which raises the same latch) pressed while the menu is open closes the whole menu from any page, Settings and its sub-pages included, like Esc at the top level. The Controls page's key capture is the exception (the menu key cancels the capture); outside a capture `controls_run` leaves like Esc (it saves) and reports "close", so `menu_loop` closes the menu too, which is the only way out of Controls for a pad-only player. Without the consume the press stayed latched and the app's service pass opened the menu again after Esc (issue #59; `tests/e2e/test_menu_toggle.py`, simulator and device: Lua app, launcher, Settings, Controls, the time-zone picker and `ui.confirm`; the native app case runs on the simulator only). The post-loop `kbd_consume_menu_press()` only matters for a press injected during teardown or after a dev `exit`.
- **OS modals take the menu key.** Each consumes the latch every pass (and a stale one at entry, next to `kbd_discard_pending`/`kbd_clear_state`, so only a press made at the dialog acts), so a press over one neither waits to open the system menu after the dialog nor closes the menu late. What it does is per modal: the file browser (Esc goes up a directory; the menu key cancels outright, from any directory), `ui_text_input`/`text_input_show` and the time-zone picker cancel, like Esc (for the menu's own modals, Wi-Fi settings and time zone, the menu stays on its page and a second press closes it). **`ui_confirm` ignores it** (the dialog stays up): No can mean "discard" to the app (the editor's and picoforge's "Save changes?"), so only a deliberate Esc/N answers. The USB-storage screen ignores it too: Esc ("Hold escape") stays its one labelled exit, so the disk is not pulled from a host mid-write. The latch is dropped by the modal, not by `kbd_clear_state()`, which keeps it (an app that calls `input.clearState()` between `input.update()` and the next service pass would otherwise lose a real press).
- **A held menu key is one press.** The STM32 repeats a held F-key, Esc and the modifiers as HOLD (no new edge) and arrows, letters, Enter, Tab, Backspace and Del as fresh PRESSED. The simulator mirrors that for SDL auto-repeat (`HOLD_REPEAT_MASK` in `simulator/hal/hal_input.c`), so a held F10 opens the menu once instead of flickering it (`tests/e2e/test_menu_key_hold.py`, an `LD_PRELOAD` shim over `SDL_PollEvent`).
- **App item callbacks run last.** An app item (`system_menu_add_item`, Lua `sys.addMenuItem`) is only recorded in the loop; its callback runs after the whole teardown (restore, free, `bg_free`, `kbd_clear_state`, the brightness save, the app's clip rect, `os_overlay_reload`), just before `menu_loop` returns. What it draws goes into the app's restored back buffer and shows at the app's next flush; it starts from a clean keyboard and may leave by longjmp (`sys.exit()`, a Lua error: `lua_menu_trampoline` uses `lua_call`) without leaking the menu's blocks or letting the Enter that chose it reach the launcher. `tests/e2e/test_menu_restore.py` covers both (simulator and device).

- **Settings → Bluetooth** (shown when `bt_pad_available()`): the Bluetooth gamepads (`src/drivers/bt_pad.h`, `src/drivers/CLAUDE.md`). Rows: the setting, "Search for controllers" (while on), the paired pads, then the devices found (not already paired; gamepads first, others dimmed); Enter toggles / searches / connects or disconnects a paired pad / pairs a found one, Del twice on the same pad forgets it, Esc goes back and the menu key closes the whole menu (as from Controls; a stale menu press is dropped at entry). The selection and Del's arming follow the device by address, since the rows are rebuilt from every poll (a search adds devices, a pairing moves one to Paired). The page polls `bt_pad_get_status()` every 250 ms into a `umm_malloc`'d page state (two ~650 B status copies: the menu runs on the 4 KB MSP at the launcher) and redraws when it changed (the report counter excluded), and calls `bt_pad_service()` on every pass so a new bond reaches `/system/bluetooth.dat` (SD work on an OS stack). A pad's D-pad and A/B drive it too. `tests/e2e/test_bluetooth.py` runs it over the simulator's scripted radio.

## UI widgets (`ui.c`, `text_input.c`)
`ui_draw_header()` (battery/WiFi/clock), `ui_draw_footer()`, `ui_draw_tabs()`, blocking modals `ui_text_input()` / `text_input_show()` and `ui_confirm()`; exposed as `picocalc.ui` / `g_api.ui`.
- **Header**: a `UI_HEADER_H` (20) bar filled row by row with a navy gradient (16-bit colour gives it ~4 visible bands; it is not dithered), a 1px border, then content: `ui_draw_header` / Lua `drawHeader` return 21. Status icons are glyph strings drawn with `display_set_pixel` and stay grey; colour is kept for alerts (battery ≤15%, WiFi `FAILED`). Battery percentage mode reads `config_get("battery_pct")` on every draw (the system menu toggle writes it). `ui_needs_header_redraw()` tracks battery, charging (`kbd_is_charging()`, bit 7 of the STM32 battery register), that setting, WiFi status and the clock. The terminal widget's default `render_y_start` stays 28 (native apps with their own 28px header rely on it); Lua apps that pair a terminal with `drawHeader` set their bounds.
- **Launcher list** (`launcher.c`): 32px rows (30px selection bar), 8 visible, 24px app icons centred in the bar (`ICON_DY`), name and description centred against them (`NAME_DY`/`DESC_DY`); `tests/e2e/test_launcher.py` mirrors these constants. `icon.png`/`icon.bmp` is scaled nearest-neighbour to 24x24 and drawn with no colour key: PNG alpha is not kept, so transparent pixels come out black. The shipped full-colour icons sit on `C_ICON_BG` (RGB 12,16,48). An app without an icon gets `draw_fallback_icon`: the `k_cart` cartridge template tinted from its category colour (`tint565`), with its first letter from the built-in 6x8 font at 2x on the label.
