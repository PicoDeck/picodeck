# Drivers (`src/drivers/`)

Subsystem notes for the firmware drivers. The root `CLAUDE.md` holds the cross-cutting rules (Core 0 never calls `mg_*`, byte-swapped framebuffer, pins only in `hardware.h`).

## Display (`display.c`)
- ST7365P 320×320 IPS LCD over **PIO0 SPI** at 100 MHz (not hardware SPI1). PIO0 is independent of the CYW43 (SPI1): no bus sharing, no lock.
- Double-buffered: `uint16_t s_framebuffers[2][320*320]` in **SRAM** (not PSRAM). `display_flush()` is a non-blocking DMA from SRAM (AHB), independent of PSRAM (QMI/XIP).
- Colors are RGB565 host-byte-order; the framebuffer stores them **byte-swapped** (panel order: the 8-bit PIO SPI DMA sends bytes as stored and the ST7365P wants big-endian), so every primitive swaps on write and every reader (screenshot, effects, `display_darken`, `display_get_pixel` behind Lua `display.getPixel`, the MCP screenshot decoder) swaps back. Native apps writing via `getBackBuffer()` write swapped pixels too (the documented contract). Image pixel buffers are host order (the blitters swap as they write), so Lua `img:getPixel/setPixel/getPixels/setPixels` and native `graphics->pixels()` see plain RGB565. The framebuffer stays in panel order: a native-order framebuffer with `channel_config_set_bswap` on the LCD DMA was scoped and rejected because it breaks that native ABI (TIC-80, C64, DOS86 in-tree; DOOM, C-Dogs, Rally out of tree; GBC is unaffected — it draws through `drawImageNN` + `flushRows`), JPEGDEC's `RGB565_BIG_ENDIAN` video path, `display_blit_be`, terminal_render and the screenshot tools (Task 18 report).
- **Clip contract**: every primitive clips its destination to the clip rect (`setClipRect`, default the screen) **once**, in int64, before any pixel loop — `drawLine(0,0,1e9,1e9)`, a radius-1e9 circle or a huge triangle cost O(visible pixels), and a primitive's own coordinates/sizes may be any int. Not covered by the int64 clip (keep these in range; Lua already rejects |v| > 2^24): `drawScaledNN`'s `img->w * scale` product, the tgx rotate path's float→int conversion, and the textured column's `y1 - y0 + 1`. Exceptions: `display_clear`, the effects and flushes (whole buffer by design); the tgx rotate path clips through a sub-view.
- The rasterisers live in `display_clip.h`, shared by `display.c` (`swap = true`) and the simulator's `simulator/stubs/driver_stubs.c` (`swap = false`), and are host-tested (`tests/unit/test_display_clip.c`) against reference per-pixel loops. The simulator has its own display implementation, so every display primitive change lands in both.
- Image blits run one of four specialised loops (opaque/keyed × flip/no-flip); a colour key of 0 means opaque. Native `drawImageNN` clips once and draws the visible part of a scaled block that straddles the clip edge. `drawScaledNN` samples column/row `d * src / dst` exactly (remainder DDA), identically in firmware and simulator.
- The image blitters build at `-O2` (`DISP_HOT`); the rest is `-Os`. They are not RAM-resident: `__not_in_flash_func` on the partial blit costs ~0.9 KB of SRAM, most of the link headroom.
- Built-in 6×8 bitmap font for ASCII 0x20–0x7E. `display_darken()` copies front → back buffer (darkened) for the system menu overlay (the firmware writes the darkened copy into both buffers; the simulator's writes only the back).
- `display_push_rect(x, y, w, h)` sends one rectangle of the back buffer to the same place on the panel as a blocking window write (CPU-fed PIO, no DMA, no swap; it waits out an in-flight flush first). The OS overlay (`src/os/os_overlay.c`) uses it for a toast or the FPS counter outside the rows of a `flushRows`/`flushRegion`; the simulator copies the rectangle into its GRAM analog. Like the partial flushes it writes GRAM rows, so it lands at a scrolled position under a non-zero scroll offset (the overlay skips it then).
- **Menu save/restore**: `display_save_buffers(dst)` copies both framebuffers (front first, then back; 2 × 200 KB) after waiting out any flush; `display_restore_buffers(src)` gives them back in their roles. Firmware steps: wait for the flush, copy the saved front into the back buffer, `display_flush()` (it swaps and presents it: the front again, on the panel), then copy the saved back into the new back buffer while the DMA reads only the front. The simulator (`driver_stubs.c`) reaches the same state directly: both buffers written in place, the front copied into its GRAM analog and presented, `s_last_presented` = front. Contents and roles come back, not which physical buffer holds each. Limit: an app that presents only with `display_flush_rows()` (no swap, GBC for example) shows its back buffer, not its front; after a restore the panel shows the saved front, stale for such an app: the rows it flushes again come back, and any row it never flushes again stays stale (no worse than the darkened remnant it replaced). `system_menu.c` uses the pair around every menu session (see `src/os/CLAUDE.md`).

## WiFi / network stack (`wifi.c`, `http.c`, `tcp.c`)
- CYW43 on SPI1; CMake defines `WIFI_ENABLED=1` for WiFi boards and all CYW43 code is `#ifdef WIFI_ENABLED` guarded.
- **Core 1 exclusively owns the Mongoose event manager** (`s_mgr`). Core 0 → Core 1 IPC is a lock-free (C11 acquire/release) 8-slot ring: `wifi_req_push()` with `CONN_REQ_HTTP_START`, `CONN_REQ_HTTP_CLOSE`, `CONN_REQ_TCP_CONNECT`, `CONN_REQ_TCP_WRITE`, `CONN_REQ_TCP_CLOSE`, `CONN_REQ_WIFI_CONNECT`, `CONN_REQ_WIFI_DISCONNECT`.
- **Close protocol** (HTTP and TCP slots): Core 0 never frees a slot Core 1 may still touch. `*_free` marks it `CLOSING` and queues the close; Core 1 detaches and stores `RELEASED`; Core 0 frees only on seeing `RELEASED` (`*_reap`). The state machines and every path are in the header comments of `http.h` / `tcp.h` — read them before changing slot lifetimes. `*_alloc` waits up to 100 ms for a slot being released; app teardown runs `http_close_all` / `tcp_close_all` (Lua: the next app's `lua_bridge_register()`; native: loader cleanup).
- **One spinlock per pool** (claimed once in `http_init` / `tcp_init`) guards state changes, pending bits, the receive rings and `in_use`; `state` is also atomic so Core 0 reads it lock-free (`http_get_state` / `tcp_get_state`, `http_get_error`, `http_get_status`, `http_headers_ready`).
- Timeouts (`http_check_timeouts` / `tcp_check_timeouts`) run on every Core 1 tick, link up or not; the link going down (`MG_TCPIP_STATE_DOWN`) fails every connection in flight with `"network down"`. A requested disconnect (`wifi_disconnect`, the SNTP auto-disconnect) runs the synchronous leave, then Core 1 stops polling Mongoose/the CYW43 until the next connect, takes the interface down itself (failing connections) and only then sets `wifi_hw_disconnected()`. Callers that change sysclk after a disconnect wait for it up to `WIFI_HW_DISCONNECT_WAIT_MS` (wifi.h, 2 s).
- Core 1 ticks every 1 ms (alarm on the Core 1 audio pool; audio pollers need that cadence); the CYW43/Mongoose poll is spaced to 5 ms while associated with no sockets open.
- **The CYW43 driver's own work runs on Core 0.** `pico_cyw43_arch_none` still uses the threadsafe_background async context, set up by `cyw43_arch_init` on Core 0 (`wifi_init`): the chip's host-wake interrupt and the driver's timers run `cyw43_poll` in that context's low-priority interrupt on Core 0 (SPARE_IRQ_4, priority 0xf0). Among them, ~2.5 s after the driver's last activity (50 sleep checks 50 ms apart), it puts the SPI bus to sleep. At a sysclk the CYW43's PIO SPI was not set up for (its divider is fixed at init, for 200 MHz), that handshake fails 64 times 1 ms apart (`[CYW43] cyw43_kso_set(0): failed`): Core 0 stalls for ~68 ms. Every video did this once, a few seconds after its 300 MHz boost (a seek's audio restart under way took the whole stall), until the video player paused the radio first. `wifi_pause_radio()` (once `wifi_hw_disconnected()` and neither connecting nor connected: the flag stays true through a connect, and Core 1 polls the chip only in those states) sleeps the bus at the current clock and sets the driver's `cyw43_poll` to NULL, so its worker does nothing (the host-wake interrupt fires at most once: its handler disables it and only a poll enables it again) and the sleep checks stop; `wifi_resume_radio()` restores it and dispatches a poll. Sleeping the bus alone was not enough: three of four runs of the four back-to-back video tests still logged one failure, in the video started just after the previous one's restore, its reconnect still in flight; paused, none in 16 video sessions. The video player pauses before its boost and resumes after its restore; `wifi_connect` resumes too. NULL is also the driver's "chip off" mark: any `cyw43_*` call that reaches `cyw43_ensure_up` while paused (a send, an ioctl, a join) would power-cycle the chip and reload its firmware, at whatever clock. Nothing does: Core 1 stops polling Mongoose after a requested disconnect, the interface is down (`mg_connect` refuses, a UDP `mg_send` fails, a TCP one only buffers), and the one request that reaches the driver, `CONN_REQ_WIFI_CONNECT`, is queued only by `wifi_connect`, which resumes first. This pokes at driver internals (`cyw43_poll`, `cyw43_sleep`, `cyw43_ll_bus_sleep`, `cyw43_schedule_internal_poll_dispatch`; cyw43-driver v1.1.0 in pico-sdk 2.2.0): recheck it on an SDK update. The launcher does the same around an app's own clock (`system_clock_khz` without `http`, after its disconnect; resumed after the clock is back at 200 MHz): Nova Rail at 300 MHz, launched with WiFi online, logged the failure 2.6 s in until it did. Both skip the pause while Bluetooth is on (Bluetooth gamepads, below): the driver stays live and the clock change retunes its bus.
- **Clock changes and the CYW43's bus** (`wifi_bus_hold`, `wifi_bus_clock`, called by `launcher_apply_clock`). The SDK sets the CYW43 PIO SPI divider once, at init (div 2: clk_sys / 4 = 50 MHz at 200 MHz, the chip's limit), so at 300 MHz the bus ran at 75 MHz. Now the clock change holds the driver's async-context lock from before the switch to after it (no CYW43 transfer, WiFi or Bluetooth, from Core 0's driver interrupt crosses it; Core 1 is paused anyway), sets the divider for the faster of the two clocks before the switch (in spec at both) and `ceil(khz / 100 MHz)` (at least 2) after it: 200 MHz keeps div 2 (nothing changes for it), 300 MHz gets div 3 (50 MHz). The state machine is found by GPIO `CYW43_PIN_WL_CLOCK`'s PIO function and its side-set pin (`cyw43_bus_pio_spi.c` keeps its PIO/SM private): recheck on an SDK update. `wifi_pause_radio()` is still done for WiFi alone; with Bluetooth on it is skipped (next bullet's section).
- Auto-connects on boot if `"wifi_ssid"` / `"wifi_pass"` exist in config. With the `"http"` requirement, WiFi stays connected after the initial time sync (otherwise it disconnects to save power).

## Bluetooth gamepads (`bt_pad.c`, `bt_pad_store.c`, `hid_pad.c`; issue #26)
- **BTstack's Classic HID host on the CYW43**, feeding `PAD_SOURCE_BT`. Off by default: the `bt_enabled` system config key (`"1"`), from Settings → Bluetooth (`system_menu.c`) or the `bt on|off` dev command. Without it nothing of Bluetooth runs: `bt_pad_init()` (boot, after `wifi_init`, before Core 1 starts) returns at once, the BT firmware is never loaded and BTstack never initialised. Built in on WiFi boards (`PICODECK_BT`, CMake option, default ON); `bt_pad_stub.c` elsewhere, `simulator/sim_bt.c` (a scripted radio) in the simulator.
- **Build.** Links `pico_btstack_classic`, `pico_btstack_hci_transport_cyw43` (which sets `CYW43_ENABLE_BLUETOOTH`, so the WiFi firmware blob becomes the WiFi+BT one) and `pico_btstack_run_loop_async_context`, not `pico_btstack_cyw43`: that one's `btstack_cyw43_init` sets BTstack up inside `cyw43_arch_init` with a flash TLV. `bt_pad.c` provides the hook (it only records the async context). `btstack/btstack_config.h`: `HAVE_MALLOC`, ACL payload 259 (L2CAP MTU 255), controller-to-host flow control as the SDK recommends for the cyw43 shared bus, 6 link keys (the 4 paired pads plus room, so a stray key never evicts a pad's).
- **Memory.** Flash +61 KB (1,192,420 → 1,253,084 B image; ~7 KB is the BT firmware in the combined blob). SRAM: 24 B. `hci.c`, `btstack_memory.c` and the CYW43's `cybt_shared_bus.c` build with `malloc`/`free` renamed to `bt_pad_malloc`/`bt_pad_free` (umm), so `hci_stack_t`, every pooled object (connections, channels, the HID connection) and the BT firmware download's ~940 B of buffers are PSRAM, allocated from the async context (umm's critical section masks interrupts, so that is safe); the rest of BTstack's static state, the SDK transport's incoming packet buffer and the CYW43 BT shared-bus driver's (~744 B of `.bss`) is linked into QMI PSRAM by `btstack/bt_psram.ld` (`.bt_psram_bss`, NOLOAD at 0x11100000: the low 2 MB of the QMI PSRAM are unused, the umm heap starts at 0x11200000) and zeroed by `setup_btstack()` before the first BTstack call; nothing reads it before (the driver reaches the transport only with `bt_loaded`). Without the script it was ~720 B of SRAM. Our own state (`bt_t`, ~2.9 KB with a 1 KB HID descriptor store and the descriptor parser's scratch) is one umm block made at the first enable and kept for the boot. The callbacks run on the MSP, so they keep big frames off it: the parser's state is in `bt_t` (`hid_pad_parse_with`), and the store's pad helpers sort references and read records in place. BLE HOGP (`pico_btstack_ble`, SM with LE Secure Connections, GATT client, HIDS client) was measured at +44 KB flash, +1.4 KB of PSRAM `.bss`, 16 B of SRAM; not built: no pad to test it with, and Classic covers the DualShock 4/DualSense/Switch Pro/8BitDo.
- **Threads.** BTstack runs on the CYW43 driver's async context (threadsafe_background, Core 0): its work and our callbacks run in that context's low-priority interrupt (on the MSP) or when Core 0 releases the context's lock (on the releasing thread's stack), never on Core 1. Every Core 0 call into it (`bt_pad_*`, from the menu, the launcher, dev commands) runs under the lock (`async_context_execute_sync`), which also makes `bt_pad_get_status()` a consistent copy. Core 1's Mongoose calls into the driver take the same lock, so BT work delays them, and the reverse. A HID report goes from the callback straight to `pad_source_publish` (any context). Power-on loads the BT firmware over the bus with the lock held: at boot before Core 1 starts; from the menu Core 1 waits on the lock meanwhile. It resumes a paused radio first (`wifi_resume_radio`: a paused driver reads as a chip that is off, and the load would power-cycle it); off then on again while BTstack is still halting goes back to initialising (`stopping`).
- **Pairing and bonds.** A search is an inquiry of ~10 s (8 x 1.28 s) and then one remote name request per unnamed device (an inquiry or name request the controller refuses with a Command Status ends that step: BTstack reports no completion for it; any search still going after 60 s is ended); the list keeps 8 (gamepads, by class of device, first and replacing others when full). Pairing is `hid_host_connect` (Report mode; SSP Just Works with NoInputNoOutput, legacy PIN "0000"); a connect asked for during a search waits for the inquiry and the name request in flight to end; a pad paired without a name (its name request failed: the one device found in the first hardware searches, a headset, never answered one) is asked again over the link once connected, and the answer sets its profile and renames its record. The link key (BTstack's TLV link key DB) and our paired-pad record (address, name, newest first, at most 4: a fifth evicts the oldest and its key) live in a tag/value store (`bt_pad_store.c`, pure, host-tested) kept in PSRAM and saved to `/system/bluetooth.dat` with `sd_atomic_write` by `bt_pad_service()` (Core 0 thread: the Bluetooth page, the launcher loop) on an OS stack, never from a callback. Not BTstack's flash TLV: it would not collide with the OTA image (offset 0, ≤ 2 MB; the bank sits 12 KB below the end of the 16 MB flash) but each write erases a sector from inside a callback with Core 1 locked out and XIP stopped. A bonded pad reconnects by paging us (switched on): page scan is on only while a pad is paired and none is connected; an unknown device that pages is refused at the ACL by a classic connection filter (`gap_register_classic_connection_filter`: only addresses with a paired record), so it can never bond with Just Works and push a pad's key out; a pairing that bonded but failed to open HID has its key dropped. A disconnect or forget while a connection is still opening (before its L2CAP channels exist `hid_host_disconnect` does nothing) drops it as it opens. A failed save of the bonds is retried after 5 s, not on every pass. One pad at a time.
- **Reports.** On `HID_SUBEVENT_DESCRIPTOR_AVAILABLE` `hid_pad_parse` reads the pad's HID descriptor (from SDP) into its gamepad fields; until then reports are dropped. Each input report (`0xA1` header stripped) goes through `hid_pad_decode` with the profile its Bluetooth name picks (`hid_pad_profile_for_name`: "Wireless Controller"/DualSense/DUALSHOCK → PlayStation, "Pro Controller" → Nintendo, "8BitDo…" → 8BitDo, else the Android/Xbox numbering; button tables from the SDL GameControllerDB's Bluetooth mappings) and is published. Face buttons by position (PAD_A bottom), the left stick past half way ORed with the hat, Home → `PAD_SOURCE_HOME`. A report shorter than its fields, or one with none (DS4's 0x11, DualSense's 0x31: vendor-defined in their descriptors), is not published, so it never releases buttons. The DS4, DualSense and Switch Pro stay in their simple report modes (0x01, 0x01, 0x3F): nothing asks them for the full ones. `HID_SUBEVENT_CONNECTION_CLOSED` (and power off) → `pad_source_disconnect`. `tests/unit/test_hid_pad.c` feeds the DS4 and DualSense Bluetooth descriptors and an Android pad's (captures: hid-tools, the kernel's HID selftests) plus the Switch Pro's 0x3F and an 8BitDo's written from documented layouts; `tests/fuzz/fuzz_hid_pad.c` fuzzes descriptor + report.
- **The radio pause and clock changes.** With Bluetooth on (`bt_pad_radio_in_use()`: powered, starting or failed), `wifi_pause_radio()` does nothing: the pause NULLs `cyw43_poll`, which BTstack's next transfer (`cyw43_ensure_bt_up` → `cyw43_ensure_up`) would read as "chip off" and answer by power-cycling the chip and reloading its firmware, and BT needs the driver polling anyway. The 300 MHz games and the video player therefore run with the driver live; the bus is retuned for the clock (WiFi bullet above) so its transfers, and the bus-sleep handshake that stalled Core 0 for ~68 ms (`cyw43_kso_set(0): failed`), stay in spec. `tests/e2e/test_bt_hw.py::test_clock_change_keeps_bluetooth` checks it on the device.
- **Measured on the device** (2026-10-02, no pad in pairing mode in range: everything but a connected pad). Power-on (BT firmware load + HCI init) ~2.5 s from `bt on`; at boot it overlaps the launcher's app scan. Boot with Bluetooth off: the same log and PSRAM figures as develop; on: WiFi, SNTP and the launcher as before, 3.6 KB less PSRAM free. WiFi, 1 MiB HTTP downloads from a LAN host (median of 3): develop 431 KB/s, this firmware with BT off 432, BT on and idle 424 (-2%), during a search 383 (-11%). Core 1's tick at the launcher with BT on: max 330 µs, none over 1 ms; during a search 272 µs. A Lua loop on Core 0 ran within ±2% with BT off, on or searching. MSP peak 2.4-2.7 KB over the BT sessions (searches from the dev command and the menu page, BT turned on inside a 300 MHz app), against 2.2-2.5 KB without BT. Turned on inside a 300 MHz app whose launch had paused the radio: up, searching, no `kso_set` failure, WiFi fine afterwards. A 300 MHz app with BT on: no `kso_set` failure, BT still on and searching afterwards; `tests/e2e/test_audio_hw.py` (MP3/QOA, the video loop, seeks and the 300 MHz boost) passes with BT on. Not measured: a connected pad (its reports' cost on Core 0, latency, the MSP on the HID path: ~0.8 KB by `-fstack-usage`).
- `bt [status|on|off|scan|scan stop|found|paired|connect <addr>|disconnect|forget <addr>]` (dev command, `dev_op_bt` in `src/dev_ops.c`; the simulator adds `bt sim …`). `tests/e2e/test_bt_hw.py`: power, search, WiFi throughput with BT off/on/searching, Core 1's tick and the MSP peak, a 300 MHz app with BT on. `tests/e2e/test_bluetooth.py`: the page, the setting and the bond file over the simulator's radio.

## TLS policy (`wifi.c`, `ca_bundle.c`, `rng.c`)
- **Verification on by default.** Every HTTPS and `tls://` TCP connection verifies the server certificate (chain to a root in `ca_bundle.c`, validity dates, host name via SNI). Failures reach Lua as `"TLS: certificate not trusted …"` / `"… expired"` / `"… does not match the host name"`.
- **SNTP gate.** Validity dates need the wall clock, so a verifying connection is refused until SNTP has set it (`clock_is_set()`), with an error starting `"clock not set"` (`WIFI_TLS_ERR_CLOCK`); if SNTP had given up, the refusal restarts it, so a retry a few seconds later works.
- **Opt-out, per connection:** Lua `conn:setInsecure(true)` (HTTP, before `get`/`post`) or `tcp:setInsecure(true)` (before `connect`); native `http->setInsecure(c, true)` or `tcp->connectEx(host, port, PCTCP_TLS | PCTCP_TLS_INSECURE)`. Skips verification and the clock gate; logs `[TLS] <host>: certificate verification DISABLED`. For self-signed dev servers only.
- **TCP TLS sockets** report connected (`TCP_CB_CONNECT`, writable) only after the handshake (`MG_EV_TLS_HS`); the connect timeout covers the handshake.
- **CA bundle**: 11 roots chosen from the chains of `store.picodeck.net`, `github.com` and `*.githubusercontent.com`, parsed once at boot (`wifi_tls_init`, on the OS stack) into one chain every verifying connection shares. `tests/unit/test_ca_bundle.c` checks it parses whole and that captured chains verify against it. The root list (with the reason for each) and the add/refresh/check workflow are in `tools/gen_ca_bundle.py` (`ROOTS` and the docstring).
- **Randomness** (`rng.c`): RP2350 TRNG (von Neumann + CRNGT + autocorrelation health tests; software-reset after every use so pico_rand never meets a halted block) → mbedTLS entropy pool → one CTR_DRBG per core, seeded only at shallow points (Core 0 on the OS stack before `wifi_init`, Core 1 at the top of `core1_entry`); Core 1 draws come from a 512-byte pool that `wifi_poll` refills. Mongoose's `mg_random` (`MG_ENABLE_CUSTOM_RANDOM`) and `picocalc.crypto` use it; `MBEDTLS_ENTROPY_HARDWARE_ALT` (get_rand_64) is off. It fails closed: no seeded/working DRBG → `mg_random` returns false with zeros (no get_rand fallback), TLS is refused, Lua `crypto.randomBytes` raises and native `randomBytes` returns false with the buffer zeroed. The `stack` dev command reports `core1_peak` (Core 1 stack painted at boot) alongside `msp_peak`.

## HTTP client (`http.c`)
- Mongoose-based HTTP/1.1 client on Core 1; static pool of 8 connections (`HTTP_MAX_CONNECTIONS`). HTTPS via `pico_lwip_mbedtls` + `pico_mbedtls` (`src/mbedtls_config.h`), certificate-verified.
- `pending` bitmask set by Core 1 (`http_ev_fn`); Lua callbacks fired by Core 0 via `http_lua_fire_pending()`, which is never re-entered (a callback that sleeps or trips the hook leaves later events for the outer call). Native apps get no callbacks (`http_fire_c_pending` is a no-op) and poll `http->isComplete()`.
- The response is parsed in `http_ev_fn` (plain `mg_connect`, no Mongoose HTTP handler): Content-Length, chunked (decoded) and close-delimited bodies (COMPLETE on the server's close; bytes that did not fit the ring are spilled and stay readable), keep-alive reuse. A body cut short (reset, early close, OOM) is FAILED, never COMPLETE.
- A request (`get`/`post`) is accepted only in IDLE/DONE/FAILED; otherwise it returns false ("a request is already in progress"). POST bodies are binary-safe. The read timeout runs from the moment the request is sent (state HEADERS), not only once headers arrive.

## TCP sockets (`tcp.c`)
- Raw TCP/TLS client on Core 1; pool of 4 (`TCP_MAX_CONNECTIONS`); non-blocking, Core 0 requests, Core 1 handles.
- Lua callbacks (`setConnectCallback` / `setReadCallback` / `setCloseCallback`) get the socket and fire from `tcp_lua_fire_pending`; events without a callback stay for `getEvents()`. `setConnectTimeout` (next `connect`, default 15 s) and `setReadTimeout` (default off) reach the connection.
- Data left in Mongoose while the ring was full moves on every poll; buffered data stays readable after the peer closes. A failed `mg_send` fails the socket. Native `tcp->close` releases the slot (the handle is invalid afterwards).

## Audio (`audio.c`, `audio_mix.c`, `sound.c`, `wav.c`, `qoa.c`, `fileplayer.c`, `mod_player.c`, `mp3_player.c`, `pcm_stage.h`)
- PWM output on GP26 (L) / GP27 (R). **One mixer** (`audio_mix.c`, which the simulator shares) sums every source per 44.1 kHz frame: the sample players (`sound.c`), the PCM stream ring (`audio_ring.h`: fileplayer, MOD, the native/Lua stream API) and the square-wave tone. It then applies the master volume and clips (in that order: turned down, a sum over full scale comes out undistorted). `audio.c` is only the output: PWM fed by a DMA channel whose completion interrupt (DMA_IRQ_0, registered on Core 1 by `audio_stream_poll`) renders the next 128 frames with `audio_mix_render`. The output starts with the first sound (`audio_output_ensure_running`, silent buffers first) and runs, silent between sounds, until the app's teardown stops it (`audio_output_stop`). Starting or stopping the stream touches neither the output nor the other sources. While the stream is stopped, pushes are dropped and `audio_ring_free()` reports 0, so the producers that pace on it (fileplayer, MOD) wait rather than race through their data. A started stream goes live (the render takes frames, and an empty ring counts as an underrun) at the first render chunk that finds data, unless it is **held**: `audio_start_stream_held` (the fileplayer's `play()`) and `audio_stream_hold` (its `pause()`, which keeps the ring) take pushes but play nothing until `audio_stream_release`. `audio_stream_drain` (a finished fileplayer) releases it and stops counting: the ring running dry is then the end, not an underrun. `audio_stream_mark_loop` notes a producer's loop point for `audiostat`. #34: started on an empty ring, the fileplayer's stream ran dry whenever Core 0 took the SD card right after `play()` (Nova Rail loads its engine sample then: tens of ms per race); held until the ring is full, the start is covered like any other moment. `audio_apply_clock()` (in `launcher_apply_clock`) re-derives the PWM divider after a clock change such as the video player's 300 MHz boost; the wrap (`OUT_PWM_WRAP` 1511, 1512 counts a frame) gives an exact 8.4 divider at every supported clock, 44,091.7 Hz (-0.02%) at each. Each source has its own lock against the render: `sound.c`'s `s_mix_cs` for the sample players, `audio_mix.c`'s `s_src_cs` for both the stream (starting/stopping: the ring clear, the rate, `s_stream_on`; held/live/ended; the underrun diagnostics) and the tone (all of its state), `mp3_player.c`'s `s_stage_cs` for the MP3 stage — striped spin locks, never nested, never held across SD, PSRAM copies, printf or umm. The MP3 player (`mp3_player.c`) is a source too.
- All WAV loaders share one RIFF chunk walker (`wav.c`, host-tested + fuzzed): 8/16-bit PCM, 1-2 channels, EXTENSIBLE resolved; float, 24/32-bit, ADPCM and >2 channels are refused. Samples keep the first 64 KB of data; the fileplayer streams **16-bit only**.
- `sound.c`: samples on a umm list with no fixed limit (Core 0 only) + 8 player slots (the voices), mixed by `sound_mixer_process()` inside `audio_mix_render` (from `audio.c`'s DMA refill ISR on Core 1). `sound_mixer_process` runs from RAM (`__time_critical_func`, its lock helpers `__force_inline`): with it in flash and gfx3d loading Core 0 (Nova Rail P3 gate), six looping voices took the refill ISR to `isr_max_us` 5260 µs (1260 µs average) of its ~2900 µs period; from RAM, 973 µs (563 µs average). Anything that frees a sample or changes which sample a player reads takes the mixer lock (`s_mix_cs`, a striped critical section); `sound_sample_destroy()` stops and detaches every player still using the sample first. A player never owns its sample. In Lua a `sampleplayer` keeps its sample alive as a user value (`sampleplayer(path)` and `sample:play()` anchor a sample of their own; `getSample()` returns that object); collected players and samples are freed / give their slots back (a player also its callback slots); freed handles hold NULL and are rejected.
- `fileplayer.c`: streaming WAV and QOA from SD. Each fileplayer owns its file (and data-chunk fields); one plays at a time on the stream. Flow control: with F stream-ring frames free, a player at speed r reads at most floor(F·r) frames, so nothing is dropped and a file plays for its real length. QOA (qoa.c) is decoded by PicoDeck's own streaming decoder, a slice-at-a-time reimplementation of the reference (third_party/qoa, MIT) that the unit tests hold it to sample for sample and the fuzz target runs; the firmware and simulator do not build the reference (the tests use its encoder for fixtures and its decoder as the oracle). One frame (≤4136 B for ≤2 channels) is read into the shared s_wav_buffer when the last is done, at most one read per tick, with sdcard_try_fread_at only (never sdcard_fsize_handle, which blocks on the SD mutex); a short read is the file's tail frame, and the next frame starts at this one's size field. Each tick then decodes only what the stream ring can take, in chunks of FILEPLAYER_READ_MIN bytes into a Core 1 stack buffer, and at most QOA_TICK_FRAMES (1024) frames, skipped ones included, so the tick after play() or a seek spreads over a few ticks: no tick decodes a whole frame (12 ms for a stereo frame from flash under load) and no PCM scratch exists. qoa_dec_run and its dequant table run from RAM (~0.65 KB of SRAM; the byte readers are force-inlined so it never calls into flash) so the decode's code does not contend with Core 0 for the XIP cache, as sound.c's mixer's does; the compressed bytes still come from s_wav_buffer in QMI PSRAM. load() counts only the whole frames the file holds (qoa_samples_in, on Core 0): a copy cut short plays and loops what is there, as a short WAV does. qoa_parse refuses a first frame shorter than min(samples, 5120) (seek geometry rests on it) and sample counts whose PCM size overflows 32 bits. position/length/seek stay virtual 16-bit PCM, so flow control, getOffset and the loop/repeat logic are the WAV path's. `setLoopRange(start, end)` (whole seconds) is `loop_bounds()`/`pass_limit()`/`wrap_position()`: a pass stops at the range end and wraps to the range start, both frame-aligned virtual-PCM positions (QOA wraps through `qoa_reposition_locked`, so it is sample exact and drops up to a frame's samples per wrap); the pushed-nothing / read-error ends-the-play rule is unchanged. `play()` starts the stream held (`audio_start_stream_held`) and the update releases it on the first tick that finds the ring (nearly) full, the tick it would otherwise wait on (a read under `FILEPLAYER_READ_MIN` would fit; QOA: the decode budget), so the stream never starts on a nearly empty ring: start latency ~10-60 ms on the device (one 4 KB WAV read per tick, 1-4 reads; one QOA frame read plus ~4 decode ticks), plus however long Core 0 holds the card. `pause()` holds the stream (the sound stops at once, the ring keeps its frames; it used to play out and then count underruns for the whole pause) and `resume()`'s next update releases it. A seek (`setOffset`) on the active player calls `audio_stream_flush_held`: while the stream is held (paused, or filling after `play()`) the ring's pre-seek audio is dropped, so the release plays the new position (without it, a seek while paused played up to a ring of the old position after `resume()`); a playing stream is left alone (the ring plays out, then the new position), and so is one another producer restarted unheld. A finished player drains the stream (`finish_locked`); every wrap marks the loop point (`wrap_locked`), and a WAV wraps on the tick that read the pass's last block (no idle tick at the loop point). Refill policy (unchanged, checked for #34): the ring is topped up whenever ≥ `FILEPLAYER_READ_MIN` bytes fit, so in steady state it stays within one such read of full (2.9 ms of 44.1 kHz stereo, 11.6 ms of 22.05 kHz mono) and a 7-12 ms read still leaves ≥78 ms of the 93 ms (44.1 kHz) ring, ≥163 of the 186 ms (22.05 kHz); only a stall longer than the ring (Core 0 holding the card) starves it, and a refill then gains 23 ms of 44.1 kHz stereo audio per 4 KB read of ~9-14 ms. `didUnderrun()` is per player: each tick compares `audio_stream_debug`'s stream underrun count with the last tick's (Core 1, under `s_lock`), armed by the player's first push after `play()`/`resume()` and latched in `underran` until Core 0's read clears it; `setStopOnUnderrun` stops the player on the tick that sees a new underrun. Lua `load` calls `fileplayer_load_err` (a static reason string) instead of the void native `filePlayerLoad`. Frames carry their own LMS state, so a seek is frame-index arithmetic (qoa_frame_offset) plus qoa_skip frames decoded and dropped (sample-exact). A read that comes back empty is the end of the file, looped like WAV's; a corrupt frame mid-file finishes the stream (never loops into it). Measured in the Nova Rail race (5 rivals, 1 lap, 300 MHz; frame work vs no music): QOA +2.1% at 22.05 kHz mono and +4.6% at 44.1 kHz stereo, WAV +2.7% and +11%; the whole-frame decode it replaced cost +3.5% and +8% (6.4 / 12.5 ms per frame from flash under load, a 32 ms Core 1 tick). Core 1's worst tick with QOA is now the frame read (~9-12 ms, SD at ~300-480 KB/s), as it is WAV's read. Core 1 stack peak 2100 of 4096 bytes with the 512-byte decode chunk.
- `mod_player.c`: pocketmod, 128 frames per update, only when the ring has room.
- `mp3_player.c`: libmad, a 32 KB PCM ring in PIO PSRAM, and an 8 KB SRAM staging buffer (`pcm_stage.h`, host-tested) that the mixer pulls through `mp3_player_mix()` (nearest-neighbour to 44.1 kHz, volume, a 64-frame fade). Core 1's update refills the stage from the ring between decode bursts. `s_stage_cs` guards the stage and whether it is mixed; the mixer holds it for a chunk, the refill for its compaction and commit, Core 0 for field updates. Stop, pause and a restarting `play` fade out and wait (at most 50 ms, at once when nothing mixes it) until the mixer has rendered the ramp; they wait without `s_mp3_mutex` so that Core 1 keeps the stage topped up meanwhile (a restart in place holds it on purpose). Stop and `play` then detach (empty the stage); pause only stops mixing and keeps the stage, so resume fades back in from where it paused; play fades in. Fed mode (the video player) keeps the stage from `start_fed` on: Core 1 stages the fed audio before `mp3_player_start_fed_output` starts mixing it, so nothing decoded is dropped. At the end of a non-looping file the stream finishes only when the ring and stage are empty, so `isPlaying()` goes false with the audio. `play()` rewinds the file. The decode loop continues only when a refill brought new data (SD busy / fed ring empty → next tick; EOF → decode the last frame, then loop back at most once per update, or finish). libmad gets only the buffered bytes, plus `MAD_BUFFER_GUARD` zeros only at the end of the input (the file's end, or fed data after `mp3_player_fed_end`): it decodes a frame only with the next header in sight, which it reads to keep the bit reservoir. With the guard always on, a frame ending exactly at the buffer's end was decoded against zeros, kept no reservoir, and the next frame was skipped (BADDATAPTR): the 4 KB refills bring a constant bitrate back to that alignment every 1.28 s at 128 kbps (5.12 s at 96 kbps; `tests/unit/test_mp3_refill.c`). In fed mode the last frame fed waits for more until the video player marks the end (a non-looping video's feeder at its last chunk); feeding again takes the end back. `mp3_player_restart_fed` restarts a playing fed session in place (a seek): holding `s_mp3_mutex`, it first tops the stage up from the PCM ring (`stage_fill`: the old audio it will play on; the refill keeps the stage only over half, ~23 ms at 44.1 kHz stereo and less while Core 1 is mid-burst, and full it holds ~46 ms), then resets the decoder and both rings behind the stage, feeds the new data and decodes into the PCM ring while the stage plays the old audio on (`s_stage_held`: no refill, the decode stops at the first frame heard); then it fades the old audio out (`fade_out_and_wait` with the mutex held: the mixer renders the ramp in the refill interrupt regardless), resets the stage (the position restarts), refills it and fades in. Silent only for the fade-out render's tail plus Core 0's reset and ≤ 4.6 KB PIO PSRAM copy: 0.48-0.55 ms on the device. That decode is not "several ms": on the device (44.1 kHz stereo at 96 kbps, the video's 300 MHz) it took 21-26 ms (#20's first in-place restart, behind the unfilled stage, ran its old audio dry at one seek in five): libmad's state reset 1.1-1.8 ms, the 16 KB prefeed copied into the fed ring 2.2-3.4 ms, the frames whose bit reservoir libmad never saw (`BADDATAPTR`, two at that bitrate, ~0.2 ms each), then the primer and the first frame heard, 8.4-10.4 ms each (`mad_frame_decode` ~5 ms, `mad_synth_frame` 3.3-4.8 ms, the PCM ring write ~0.5 ms; Core 1 takes ~13 ms a frame meanwhile, beside the JPEG decode). The ~91 ms restarts seen then were not the decoder: the CYW43 driver stalled Core 0 for 68 ms once per video (see WiFi), and a restart under way took the whole stall. It stops before a frame that might outlast the old audio (`s_hold_deadline`: the stage's audio less a 6 ms guard for the switch, against the longest frame so far, at least 12 ms); the old audio then fades out while it still plays and the rest is decoded from silence (`late` in the restart stats: a gap of a frame or two, still shorter than `start_fed`'s). Mid-stream (`mid_stream`) it first decodes one frame it does not play (`s_prime_frames`): from empty, the synthesis filterbank and IMDCT overlap play the first frame as ~5 ms of zeros then a quiet ramp. Refused (false, nothing changed) when nothing is audible (not mixing, paused, the output off): the caller restarts through `start_fed`, silent from the fade-out until `start_fed_output`'s pre-roll is decoded. `mp3stats` prints the restart diagnostics (`mp3_player_fed_restart_stats`: in-place restarts and fallbacks, the gap on Core 0's clock, the decode behind the old audio, the old audio left and the late ones).
- `mp3_player_update()`, `fileplayer_update()` and `mod_player_update()` run on Core 1 every 1 ms tick.
- **MP3 costs the app's core too.** Core 1's decoding contends with Core 0 for the shared XIP cache and QMI (flash + PSRAM). In a gfx3d game at 200 MHz (Nova Rail P3 gate), 44.1 kHz stereo MP3 made every Core 0 frame section ~2.1× slower, 22.05 kHz mono ~1.24×; 300 MHz did not rescue it. A looping WAV via the fileplayer (SD over SPI, tiny code) cost 2.5% (22.05 kHz mono) / 15% (44.1 kHz stereo). A MOD via `mod_player.c` (pocketmod on Core 1, samples read from QMI PSRAM, code in flash) cost 14% (4 channels) / 24% (8 channels) with busy test modules; moving pocketmod's mix loop into RAM is the likely lever. QOA via the fileplayer is cheaper still (see the fileplayer bullet); `docs/API-Audio-and-Sound.md` tells apps to use QOA, then WAV, for real-time music.
  - **Where libmad lives** (issue #28, from the firmware map). Code: only `synth.c` is in SRAM (`libmad_ram`, `.time_critical.libmad`, 4.9 KB: `dct32`, `synth_full`); the rest runs from XIP flash: `layer3.c` 11.3 KB (`mad_layer_III` 7.7 KB with Huffman decode, requantisation and stereo inlined, `III_imdct_l` 2.1 KB, `III_imdct_s`, `III_aliasreduce`), `bit.c` (`mad_bit_read`), `frame.c`, `timer.c` (~6 KB together). Tables, all in flash `.rodata`: `rq_table` 32 KB (indexed by the decoded magnitude: mostly its first entries), Huffman 13 KB (the region's 0.1-2.4 KB tables), `D[17][32]` 2.2 KB (the RAM-resident synth's window, read whole for every 32 samples of each channel: its code is in SRAM, its table is not), small sfb tables. State, three `umm_malloc` blocks in cached QMI PSRAM: `mad_stream` 2.6 KB (main_data reservoir), `mad_frame` 20.3 KB (`sbsample` 9 KB, `overlap` 4.5 KB, and this port's `xr_raw` 4.5 KB + `tmp` 2.3 KB, moved off the stack), `mad_synth` 8.5 KB (`filter` 4 KB, `pcm.samplesX` 4.5 KB): 31.4 KB, twice the cache. The 8 KB input buffer and the 8 KB stage are static SRAM; the PCM ring is PIO PSRAM, written by an 8-bit DMA that reads the PCM back from QMI PSRAM through the uncached alias after cleaning its lines: one QMI transfer per byte (176 k/s at 44.1 kHz stereo, 44 k/s at 22.05 kHz mono). The traffic: a 44.1 kHz MPEG-1 frame is 2 granules × 2 channels, a 22.05 kHz MPEG-2 mono frame 1 × 1, both 38.3 frames/s, so 153 vs 38 granule-channels/s (4:1). Each one runs ~11 KB of flash code over a few KB of tables and ~8 KB of state, sweeping the whole 16 KB cache (Core 0's working set with it): at least ~3 k line fills and ~1 k dirty write-backs, so ≥ ~0.6 M QMI transfers/s at 44.1 kHz stereo against ~0.15 M at 22.05 kHz mono (estimates; `xipstat` measures). The measured extra Core 0 time (+110% / +24%) is ~4.6:1, in line with that 4:1. **No SRAM for any of it**: the link leaves ~1 KB over the 2 KB minimum heap, Core 1's 4 KB stack (SCRATCH_X, 2.1 KB peak) and Core 0's MSP (SCRATCH_Y) are full. Candidates if SRAM is found: `D[]` (2.2 KB) next to the synth; an SRAM bounce for the PCM ring write (4.6 KB) to end the byte-wise uncached reads; `pio_psram.c`'s static 4 KB `s_dbg_buf` (the `psram` dev command's only) is the one reclaimable buffer seen.
  - **When it decodes** (`mp3_sched.h`, host-tested with a pipeline model in `tests/unit/test_mp3_sched.c`): a burst of up to 3 frames when the PCM ring is at or below half (the old rule, kept as the floor: whatever Core 0 does), and **ahead** while a paced app's Core 0 waits in `perf_end_frame` (`os/core0_idle.h`: the pacing wait publishes its deadline, lock-free) with at least one frame's decode time (`frame_us`, an estimate from frames that finished inside a window, seeded at 3 ms) left in the window. So with `perf.setTargetFPS` and idle time at the end of each frame the decoding lands there; an app that never paces, or whose frames run late, opens no window and decodes exactly as before. Fed mode (the video player) never decodes ahead. A frame started in a window may run past its end (`mp3_overran`). **Awaiting hardware measurement** (the procedure is in the issue #28 report; `tests/e2e/test_mp3_contention_hw.py`). `xipstat` reports `mp3_low_frames`/`mp3_idle_frames`/`mp3_overran`/`mp3_frame_us`, Core 0's `idle_windows`/`idle_ms`, and `xipstat mp3idle off|on` switches decoding ahead for an A/B run; the simulator's `get_mp3_stats` RPC reports the same (`tests/e2e/test_mp3_pacing.py`: no underrun paced or unpaced, 44.1 kHz stereo and 22.05 kHz mono). A mono frame goes to the ring in one write (packed in place in `samplesX`), not one 2-byte PIO PSRAM transfer per sample.
- `audiostat [reset]` (dev command, `dev_op_audiostat` in `src/dev_ops.c`, which the simulator's `dev_command` RPC runs too): Core 1's tick cost (ticks, over 1 ms, missed, the longest) and the audio output's refill interrupt (count, time, the longest), stream and MP3 underruns, busy sample voices, `sys_khz`, then when the stream ran dry (`audio_stream_get_stats`): `stream_starts`, `stream_loops` (loop points marked), `stream_gaps` (runs of starved 32-frame render chunks), `stream_start_underruns` (in a stream's first second of content), `stream_loop_underruns` (in the second after a loop point), `stream_first_ms` / `stream_last_ms` (where the first and last gap began, ms into the stream's content; -1 none) and `stream_low_ms` (the ring's low-water mark while live; -1 none). The render keeps them in one struct under `s_src_cs`: a chunk that ran dry calls `stream_note_starved` (flash-resident on purpose: only the slow path, already an audible gap, calls out), any other live chunk costs a store and the low-water compare; positions are the ring's read counter, converted on Core 0. `reset` starts a new window (Core 1 zeroes its tick counters at its next tick, the refill interrupt its own at its next refill: Core 0 only raises a flag, since a direct write would race their read-modify-writes; the stream's under the lock). Parsers read `key=value` pairs: add fields, never rename one. `tests/e2e/test_audio_hw.py` and Nova Rail's `tools/hw_lap.py` measure with it; `tests/e2e/test_fileplayer.py` checks the stream fields on both targets. SRAM for #34: the RAM-resident render grew 84 B (612 to 696, plus an 8 B veneer to the helper) and the state 60 B; with the helper inlined the render grew 176 B.
- **Locks (Core 0 ↔ Core 1)**: each player has a mutex (`fileplayer.c` `s_lock`, `s_mod_mutex`, `s_mp3_mutex`) guarding its file / data / state. Core 0 takes it blocking. The fileplayer and MOD player take it only for field updates (their files are opened, closed and freed outside it, after detaching). The MP3 player does SD work under it on Core 0: `load()` opens (and closes) the file, `play()` rewinds it with a blocking seek and read and runs the pre-fill decode, and `stop()`, `start_fed`, `reset` and `deinit` close it (`sdcard_fclose`), all holding `s_mp3_mutex`; Core 1's update skips meanwhile. `restart_fed` (a video's seek) also holds it on Core 0 across a decode (the primer and the first frame heard: 21-26 ms on the device, never longer than the old audio in the stage) and the wait for the fade-out's render (a render period, 50 ms at most), so that nothing new reaches the stage before the old audio has faded out; the refill interrupt never takes it, so the render goes on. Core 1's update only ever **try-locks** it and skips the tick. Core 1 never blocks on the SD card either: it reads with `sdcard_try_fread_at()` (seek + read under one try-lock, `SDCARD_BUSY` when Core 0 holds the card) and keeps its own file offset — Core 1 reads only through `sdcard_try_fread_at()`, never `sdcard_fseek`.
- Volume (master, MP3) scales the signed sample about PWM mid-scale; silence is always `PWM_MID`. Volumes are 0-100 everywhere (`audio.setVolume`, sampleplayer, fileplayer, mp3player, modplayer); larger values clamp to 100 (the mixers scale by vol/100). The app teardowns (`lua_runner.c`, both `native_loader.c` paths) reset the master volume to 100.
- The simulator runs all of it (`audio_mix.c`, `sound.c`, `mp3_player.c`, `fileplayer.c`, `mod_player.c`); `simulator/sim_audio.c` replaces only `audio.c`'s output.

## Video player (`video_player.cpp`)
- MJPEG with JPEGDEC (decoder state in static SRAM). Frame pool (3×96 KB JPEG buffers) in QMI PSRAM; Core 1 prefetches frame N+1 from SD while Core 0 decodes frame N.
- The frame index is sized from the AVI header (cap `VIDEO_MAX_FRAME_INDEX`); beyond the cap playback/seek fall back to sequential chunk scanning. The audio chunk index (`avi_index.h`, host-tested) is sized from the audio stream header (VBR MP3: dwLength counts the chunks; never more than the movi list can hold, movi_size / 8; the frame-count estimate if that allocation fails) and grows during the movi scan: a 10 fps clip has ~4 MP3 chunks a frame, and a chunk the index misses never plays.
- Seeks clamp and never wrap; with loop off the last frame is held (`ended`). Built-in progress OSD drawn into the frame after decode. Hardware-only (the simulator stubs it).
- Audio is MP3 fed mode (`mp3_player_start_fed`, Core 0 feeding chunks from the index each `update()`). A loop keeps the session: with loop on, the feeder goes on past the last chunk from the first and marks the loop point (`mp3_player_fed_mark`); the decoder notes the PCM frame where it starts, and at the video's end `loop_with_audio` sets the video clock from how far the mixer is from it (`mp3_player_fed_mark_reached`: the audio's loop point within ±200 ms of the video's end by its clock; the last frame holds while it is still to come, and while the decoder, only ~0.1-0.8 s ahead of the mixer, has not reached it), else both restart. The first frame of an MP3 stream uses no bit reservoir, so the decoder plays through the wrap (`tests/unit/test_mp3_fed.c`). A seek reads the new position's first chunks into a 16 KB prefeed while the old audio still plays, then, playing, restarts the session in place (`mp3_player_restart_fed`): the decoder starts on the prefeed while the old audio, topped up first, plays on, and the old fades into the new (the gap: the fade-out render's silent tail and Core 0's switch, 0.48-0.55 ms over 132 seeks on the device, none late; `test_audio_hw.py::test_video_seeks_keep_the_audio_fed` gates it through `mp3stats`). The prefeed starts a chunk before the cursor's, the decoder's primer, so the first frame heard is the one an unprimed restart from the cursor's chunk played first (libmad drops that chunk's own frame, whose bit reservoir it never saw; at chunk 1 the primer is chunk 0, which needs none, and chunk 1 is heard). Paused, or with nothing audible, the session restarts through `start_fed` from the cursor's chunk (silent from the fade-out until the pre-roll is decoded: three frames, ~10 ms, plus the `s_mp3_mutex` waits and the decoder's ~5 ms ramp up from zeros). Paused, a (re)start defers its output (`audio_output_pending`) to `resume()`. The player keeps the volume and applies it after every `start_fed` (which resets it to 100).

## QMI PSRAM (`qmi_psram.c`)
- **XIP cache**: 16 KB, 2-way, 8-byte lines, shared by both cores, the DMA, flash (CS0, SCK 100 MHz at 200 MHz) and QMI PSRAM (CS1, ≤ 75 MHz); a miss is one QMI transfer, an uncached-alias access one per access. **`xipstat [reset|off|prio core0|prio none|mp3idle on|mp3idle off]`** (dev command, `src/os/xip_stats.c`): `reset` starts a window (the XIP cache's access/hit counters plus the bus fabric's XIP-port downstream stall cycles and contested accesses, harvested into 64-bit totals by a 10 ms Core 0 timer; they saturate otherwise: 32-bit ~40 s, 24-bit 84 ms of stalls), a window started in an app (or that sees one start) freezes when that app exits, a bare `xipstat` prints one `key=value` line (`acc hit miss hit_pm stall0/1 contested0/1 …`). The counters cannot tell the cores apart: compare windows. `prio core0` sets Core 0 high bus priority (BUS_PRIORITY, every port) for an A/B run, until `prio none` or the app's exit (the launcher clears it). The XIP counters are write-to-clear, not read-to-clear; `sys.getMemInfo().xip_cache_hit_rate` is the rate since its previous call (-1 after ~40 s without a harvest: saturated).
- The onboard 8 MB chip on CS1, quad mode; `qmi_psram.h`'s `qmi_psram_timing()` derives CLKDIV/MAX_SELECT/MIN_DESELECT safe at any single clk_sys OR (for a clock change in flight) safe at both ends at once, since a bare "recompute for the new clk_sys" leaves PSRAM running at the OLD divider — beyond its validated SCK — from `set_sys_clock_khz` until something retimes it. `launcher_apply_clock` pre-scales with the latter (`qmi_psram_prescale_timing`) before the switch and retimes with the former (`qmi_psram_update_timing`) after.

## PIO PSRAM (`pio_psram.c`)
- Second 8 MB PSRAM on the mainboard, via PIO1 SPI; bus independent of QMI PSRAM/flash XIP. `pio_psram_init()` runs early in `main()`; non-fatal if the chip is absent.
- Layout (`pio_psram.h`): MP3 PCM ring `0x0000` (32 KB), a video region `0x8000` (256 KB) reserved for the OS but unused (the video frame pool lives in QMI PSRAM), apps from `PIO_PSRAM_APP_BASE` = `0x48000`.
- App access is limited to `[PIO_PSRAM_APP_BASE, chip end)` by `pio_psram_app_range_check` (64-bit, host-tested): Lua `sys.pioPsramRead/Write` raise on anything overlapping the OS region, negative, or past the chip; native `g_api.psram->pioRead/pioWrite/pioBulkRead/pioBulkWrite` (`src/main.c`) do nothing on a refused call (a read leaves `dst` untouched) and log `[NATIVE] psram->… refused`.
- DMA vs the XIP cache (`pio_psram_xip.h`): a source in cached QMI PSRAM (`0x11…`) has its lines cleaned (`xip_cache_clean_range`) and is read through the uncached alias; a cached destination gets whole lines DMA'd with `xip_cache_invalidate_range` before and after, and its partial end lines copied by the CPU from a bounce buffer (invalidate only lines the transfer owns entirely). Transfers hold the driver lock one 4 KB segment at a time and yield it to a waiting core between segments.

## Keyboard (`keyboard.c`, `kbd_event_queue.h`)
- The STM32 keyboard controller (I2C1, 10 kHz: 100 kHz locked it up after extended use) queues `[state, keycode]` items in a FIFO: state 1=pressed, 2=hold, 3=released; keycode is ASCII for printable keys (already shifted) or a `KEY_*` code. Released items are confirmed for buttons and for letters (Z and X held and released throughout a Nova Rail playtest, 2026-09-28, no key stuck); **hardware-pending**: which keycode a shifted symbol is released under (`!` vs `1`), until the device checklist in the Task 20 report runs.
- **Bus engine** (`kbd_i2c.c`; scheduling in the pure, host-tested `kbd_bus.c`): after `kbd_init()`'s probe, all STM32 traffic runs asynchronously on Core 0, driven by the I2C1 interrupt and default-alarm-pool alarms. That covers FIFO reads, the battery read (every 5 s; `kbd_get_battery_percent` returns the latest) and backlight writes (queued, latest wins, first in line). Nothing waits on the bus; the old blocking poll cost 107 ms/s of Core 0.
  - It reads the FIFO back to back while items come, then 10 ms after it reads empty. A due FIFO read goes before a due battery read (the battery follows at once). `kbdstat` `max_gap_us` is the time from an empty answer to the next read's result: ~16 ms (the 10 ms interval plus a ~6 ms read). A key pressed just after the STM32 answered empty also waits out the rest of that read, so the worst key-to-ring latency is ~22 ms; a backlight write (rare: dimming, the menu) goes first and can add ~3 ms.
  - Items wait in a 16-entry ring; `kbd_poll()` decodes up to 8 of them per poll (`KBD_POLL_MAX_ITEMS`), so one poll's events always fit the 16-entry event queue. A full ring stops the reads and the STM32 keeps the rest.
  - Engine steps run with interrupts disabled for a few µs; task-side calls touch its state under the same mask.
  - `kbd_discard_pending` is non-blocking: it empties the ring, and the engine drops items until a FIFO read begun after the call reads empty.
  - A failed transaction (NACK, timeout) stops the engine. The next `kbd_poll()` runs the ~12 ms bit-banged bus recovery in task context: at once for the first 10 failures in a row, then at most every 100 ms.
  - Clock changes pause it: `kbd_pause_bus` in `launcher_apply_clock`, resumed by `kbd_apply_clock`.
  - Deliberate resets (dev `reboot`/`reboot-flash`, the system menu, `sys.reboot`, OTA, the out-of-memory reboot) call `kbd_prepare_reset()` first, so a reset never cuts an STM32 transaction mid-byte (an interrupted transaction can lock the STM32's I2C slave until a power cycle). Resets nobody prepares:
    - HardFault: `hardfault_c` (either core) first calls `kbd_i2c_halt()`, a set-once flag (one store, safe from a fault handler) that stops the engine at its next job boundary; nothing resumes it. A Core 1 fault leaves Core 0 running the engine, which finishes the transaction in flight (~6 ms) and starts no other, long before the handler resets 3 s later. On a Core 0 fault the engine is frozen anyway (its interrupts cannot preempt HardFault), and the 3 s hold lets a transfer already queued in the I2C block finish.
    - Watchdog: FIFO and battery reads stop when `kbd_poll()` (or `kbd_poll_background`) has not run for 1 s (`KBD_BUS_UNPOLLED_US`, in `kbd_bus.c`); backlight writes still go, and the next poll reads the FIFO at once. A Core 0 stall that trips the watchdog (a native app that stops calling `sys->poll()`: ≥ 10 s) therefore finds the bus idle. Nothing is lost: the STM32 keeps the items, as with a full ring; a key pressed meanwhile reaches the app one poll later than it would have. The same happens at boot: the engine reads for a second after `kbd_init()` (the battery included), then waits for the launcher's first poll; the boot backlight writes (`kbd_set_backlight` after `kbd_init` and after `config_load`) still land.
    - Still exposed: a watchdog reset less than 1 s after the last poll that lands mid-transaction (the bus is busy ~37% of the time while polled), and brown-out or power loss.
  - USB storage mode stretches the idle interval to 500 ms (`kbd_set_poll_interval_ms`); items still come back to back, and the battery every 5 s.
  - It stays on Core 0, because `sys.pauseBackground` stops Core 1.
- Dev command `kbdstat` (`reset` zeroes, `fault` NACKs the next transaction) prints the engine's counters and `sys_khz`. `tests/e2e/test_kbd_hw.py` checks cadence, cost, recovery, a clock change, the stop while nobody polls and idle dimming on the device; its timing fixtures keep harness commands out of their windows (every dev command is answered inside the app, in a service pass that stalls it a few ms).
- Every item is decoded in order (`kbd_fifo_apply`, header-only, shared with the simulator and `tests/unit/test_kbd_event_queue.c`) into a 16-event queue (`pollEvent`; oldest dropped), a key-down set (`isKeyDown`: reliable for buttons and letters (case-folded because Shift may come up first); shifted symbols pending hardware confirmation; a key stuck down is cleared by `clearState()`/`kbd_clear_state`), a 4-char `getChar` backlog (still one char per poll) and the button masks. A press+release inside one poll reads as held for that poll.
- HOLD is a repeat of a press already seen (repeat-flagged events and a char, no press edge). A HOLD for a key pressed before `kbd_clear_state`/`kbd_discard_pending` only marks it held and "unseen": every later HOLD of it stays quiet until it is released and pressed again. That covers only the keys the controller repeats as HOLD (F-keys, Esc, modifiers, shifted codes): arrows, letters, Enter, Tab, Backspace and Delete repeat as PRESSED items every 100 ms, which decode as fresh presses. So a held 'y' does answer `ui_confirm` once it is armed (it reads y/n through `getChar` with no held check); Enter is safe (it needs a fresh Enter press edge). Known, not yet fixed.
- **Gamepad** (`PAD_*`, `kbd_get_pad*`): the same decode resolves every key transition through the pad map (`kbd_padmap_t`: 12 buttons x primary/alternate keycode, `kbd_set_pad_map`; letters case-folded) to a map slot, tracked down/up in `kbd_pad_t.down`; a button is held while any of its slots is down. The masks live in `kbd_buttons_t.pad` and follow the button masks' rules (tap inside one poll held for that poll, a HOLD of an unseen key held without an edge, background runs, the idle-dim swallow). Aliasing, not remapping: the key still reports as itself. FIFO items go through `kbd_fifo_apply_pad`, the simulator's staged events through `kbd_pad_event`, injected buttons through their keys' slots (down when published, up on retire/keyup, kept quietly held across `kbd_clear_state`), an injected char taps its button at the next foreground poll. `kbd_clear_state`/`kbd_discard_pending` and a map change drop the gamepad state.
  - **Shift/Alt mid-hold.** The controller recomputes a key's code at every transition from the modifiers held then (`picocalc_keyboard` `keyboard.ino` `transition_to`): under Shift, F1-F5 are F6-F10, Del End, Tab Home, Enter Insert, Esc Brk, Up/Down PgUp/PgDn, and Left/Right/Backspace/Space send nothing; under Alt, B and Space send nothing and I sends Insert (only their press and release: their repeats come as plain PRESSED items). The gamepad tracks Shift and Alt from their own items (`kbd_pad_t.mods`, always sent: the controller's `reg_init` sets `CFG_REPORT_MODS|CFG_USE_MODS` at every boot), folds the shifted codes back (`kbd_key_unshift`; F10 and Brk, the menu and screenshot keys, only ever release a button), releases the silenced keys' buttons when the modifier goes down, and ignores B, I and Space presses while Alt is held. The shifted codes fold back whatever the tracked Shift state, because the controller clears its own modifier flags one scan (≥ 17 ms) after it reports them up and scans matrix keys before the side buttons, so they still arrive just after Shift's RELEASED. Insert is also Alt+I (with or without Shift, and just after Alt goes up): its press only taps Enter's button, its HOLD (only Enter repeats as one) holds it, its release releases it unless Alt alone is tracked. A key pressed within a scan of Shift going up may miss its press edge (Left, Right, Backspace, Space, Enter). Two cases leave a button held until `kbd_clear_state`: Enter released within a scan of Shift going up while Alt is held, and B, I or Space held under the controller's num lock (LShift and Alt pressed together turn it on, a lone Shift press turns it off; it acts as Alt held, and only a register read could see it, which the bus engine does not do). A randomized model of the controller firmware (100k runs) finds nothing else held. `BTN_*` and the key-down set do not do this (a key released under its shifted code stays held there until `kbd_clear_state`).
  - The controller repeats arrows, letters, Enter, Tab, Backspace and Delete as PRESSED items, F-keys, Esc, modifiers and the shifted codes as HOLD: only the latter get the quiet-hold-after-clear rule.
  - Host-tested in `tests/unit/test_kbd_pad.c` (replays of those sequences). SRAM: 16 B of gamepad state in `s_btn`, the 24 B map, 2 B of injected char taps.
- **Pad sources** (`pad_source.c/.h`, pure, host-tested in `tests/unit/test_pad_source.c`; issue #26): everything else that drives the gamepad reports its whole `PAD_*` state as a source: `PAD_SOURCE_TEST` (the `pad` dev command, `dev_op_pad` in `src/dev_ops.c`), `PAD_SOURCE_HOST` (the simulator's SDL controllers, `simulator/hal/hal_pad.c`), `PAD_SOURCE_BT` (a Bluetooth pad, `bt_pad.c`: Bluetooth gamepads above), `PAD_SOURCE_USB` reserved. `kbd_get_pad*` return the keyboard aliases' masks ORed with the sources' (`pad_sources_combine_*`): held while any source holds it, one press and one release edge, no repeats; `getLabel` still names the key.
  - Producer side (a transport, any core or ISR, one producer per source): `pad_source_publish(id, state)` once per report with the whole state (connects the source), `pad_source_disconnect(id)` on link loss (its buttons release at the next poll; nothing sticks). A publish is an atomic store of the state word (bit 31 = connected) then, when buttons went down, an atomic OR of them into the source's latch word; Core 0 loads the state before it takes the latch (`atomic_exchange`), so a press and release between two polls still read as a one-poll tap and a press already seen released can never come back from the latch as a second press. Cross-core LDREX/STREX works on the RP2350's SRAM (global exclusive monitor; the SDK's software spin locks rely on it).
  - Consumer side, Core 0 in `kbd_poll`/`kbd_poll_background` (`pad_sources_poll`): foreground polls move `curr`/`prev` on; background polls (sys.sleep) only gather taps for the next foreground poll. `PAD_SOURCE_HOME` (bit 16) is not a button: its rising edge sets the menu flag (`kbd_consume_menu_press`, the Sym key's path), at once in background polls too. `kbd_clear_state` keeps a seen-and-held button held without a new edge (an unpolled press keeps its edge); `kbd_discard_pending` drops unpolled taps (Home included) and makes every held button quiet; the idle-dim wake swallows the poll's fresh pad presses (held ones come back quietly). The test source's timed hold (`pad a 100`) starts at the first foreground poll after the command.
  - The OS's own menus read pad presses as navigation (`kbd_get_pad_nav_pressed`: sources only, D-pad = arrows, A = Enter, B = Esc): the launcher and the system menu's main loop, so a pad-only player can open the menu with Home, wrap Up to Exit App and choose it. The Controls page, text input and other dialogs are keyboard-only.
  - The header (`ui.c`) shows a gamepad glyph left of the WiFi icon while any source is connected (`pad_sources_connected`), the test source included.
  - What a transport adds: discovery/pairing and the link, the report parser, the physical -> logical map (face buttons, shoulders, Start/Select, D-pad, a stick with a deadzone, Home), then one publish per report and a disconnect on link loss. SRAM: 4 x 12 B of source slots plus ~22 B of Core 0 state.
- `kbd_clear_state` also clears the queue; `lua_bridge_input_init` flushes it, so an app never receives the launcher's keys. Injected buttons/chars feed the queue too; in the simulator `hal_input.c` stages events and `kbd_poll` moves them in, so apps see them only after `input.update()`, as on hardware. On the device an injected key still down at `kbd_clear_state` (an active one-shot such as the injected Enter that opened the modal, or a `keydown` latch) stays held with no press edge and releases on retire/`keyup`; a still-pending injection is published with its edge by the next poll; an unread injected char is dropped (`kbd_inject_*` in `kbd_event_queue.h`, host-tested).
