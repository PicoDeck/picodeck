# Drivers (`src/drivers/`)

Subsystem notes for the firmware drivers. The root `CLAUDE.md` holds the cross-cutting rules (Core 0 never calls `mg_*`, byte-swapped framebuffer, pins only in `hardware.h`).

## Display (`display.c`)
- ST7365P 320×320 IPS LCD over **PIO0 SPI** at 100 MHz (not hardware SPI1). PIO0 is independent of the CYW43 (SPI1): no bus sharing, no lock.
- Double-buffered: `uint16_t s_framebuffers[2][320*320]` in **SRAM** (not PSRAM). `display_flush()` is a non-blocking DMA from SRAM (AHB), independent of PSRAM (QMI/XIP).
- Colors are RGB565 host-byte-order; the framebuffer stores them **byte-swapped** (panel order: the 8-bit PIO SPI DMA sends bytes as stored and the ST7365P wants big-endian), so every primitive swaps on write and every reader (screenshot, effects, `display_darken`, the MCP screenshot decoder) swaps back. Native apps writing via `getBackBuffer()` write swapped pixels too (the documented contract). The framebuffer stays in panel order: a native-order framebuffer with `channel_config_set_bswap` on the LCD DMA was scoped and rejected because it breaks that native ABI (TIC-80, C64, DOS86 in-tree; DOOM, C-Dogs, Rally out of tree; GBC is unaffected — it draws through `drawImageNN` + `flushRows`), JPEGDEC's `RGB565_BIG_ENDIAN` video path, `display_blit_be`, terminal_render and the screenshot tools (Task 18 report).
- **Clip contract**: every primitive clips its destination to the clip rect (`setClipRect`, default the screen) **once**, in int64, before any pixel loop — `drawLine(0,0,1e9,1e9)`, a radius-1e9 circle or a huge triangle cost O(visible pixels), and a primitive's own coordinates/sizes may be any int. Not covered by the int64 clip (keep these in range; Lua already rejects |v| > 2^24): `drawScaledNN`'s `img->w * scale` product, the tgx rotate path's float→int conversion, and the textured column's `y1 - y0 + 1`. Exceptions: `display_clear`, the effects and flushes (whole buffer by design); the tgx rotate path clips through a sub-view.
- The rasterisers live in `display_clip.h`, shared by `display.c` (`swap = true`) and the simulator's `simulator/stubs/driver_stubs.c` (`swap = false`), and are host-tested (`tests/unit/test_display_clip.c`) against reference per-pixel loops. The simulator has its own display implementation, so every display primitive change lands in both.
- Image blits run one of four specialised loops (opaque/keyed × flip/no-flip); a colour key of 0 means opaque. Native `drawImageNN` clips once and draws the visible part of a scaled block that straddles the clip edge. `drawScaledNN` samples column/row `d * src / dst` exactly (remainder DDA), identically in firmware and simulator.
- The image blitters build at `-O2` (`DISP_HOT`); the rest is `-Os`. They are not RAM-resident: `__not_in_flash_func` on the partial blit costs ~0.9 KB of SRAM, most of the link headroom.
- Built-in 6×8 bitmap font for ASCII 0x20–0x7E. `display_darken()` copies front → back buffer (darkened) for the system menu overlay.

## WiFi / network stack (`wifi.c`, `http.c`, `tcp.c`)
- CYW43 on SPI1; CMake defines `WIFI_ENABLED=1` for WiFi boards and all CYW43 code is `#ifdef WIFI_ENABLED` guarded.
- **Core 1 exclusively owns the Mongoose event manager** (`s_mgr`). Core 0 → Core 1 IPC is a lock-free (C11 acquire/release) 8-slot ring: `wifi_req_push()` with `CONN_REQ_HTTP_START`, `CONN_REQ_HTTP_CLOSE`, `CONN_REQ_TCP_CONNECT`, `CONN_REQ_TCP_WRITE`, `CONN_REQ_TCP_CLOSE`, `CONN_REQ_WIFI_CONNECT`, `CONN_REQ_WIFI_DISCONNECT`.
- **Close protocol** (HTTP and TCP slots): Core 0 never frees a slot Core 1 may still touch. `*_free` marks it `CLOSING` and queues the close; Core 1 detaches and stores `RELEASED`; Core 0 frees only on seeing `RELEASED` (`*_reap`). The state machines and every path are in the header comments of `http.h` / `tcp.h` — read them before changing slot lifetimes. `*_alloc` waits up to 100 ms for a slot being released; app teardown runs `http_close_all` / `tcp_close_all` (Lua: the next app's `lua_bridge_register()`; native: loader cleanup).
- **One spinlock per pool** (claimed once in `http_init` / `tcp_init`) guards state changes, pending bits, the receive rings and `in_use`; `state` is also atomic so Core 0 reads it lock-free (`http_get_state` / `tcp_get_state`, `http_get_error`, `http_get_status`, `http_headers_ready`).
- Timeouts (`http_check_timeouts` / `tcp_check_timeouts`) run on every Core 1 tick, link up or not; the link going down (`MG_TCPIP_STATE_DOWN`) fails every connection in flight with `"network down"`. A requested disconnect (`wifi_disconnect`, the SNTP auto-disconnect) runs the synchronous leave, then Core 1 stops polling Mongoose/the CYW43 until the next connect, takes the interface down itself (failing connections) and only then sets `wifi_hw_disconnected()`. Callers that change sysclk after a disconnect wait for it up to `WIFI_HW_DISCONNECT_WAIT_MS` (wifi.h, 2 s).
- Core 1 ticks every 1 ms (alarm on the Core 1 audio pool; audio pollers need that cadence); the CYW43/Mongoose poll is spaced to 5 ms while associated with no sockets open.
- Auto-connects on boot if `"wifi_ssid"` / `"wifi_pass"` exist in config. With the `"http"` requirement, WiFi stays connected after the initial time sync (otherwise it disconnects to save power).

## TLS policy (`wifi.c`, `ca_bundle.c`, `rng.c`)
- **Verification on by default.** Every HTTPS and `tls://` TCP connection verifies the server certificate (chain to a root in `ca_bundle.c`, validity dates, host name via SNI). Failures reach Lua as `"TLS: certificate not trusted …"` / `"… expired"` / `"… does not match the host name"`.
- **SNTP gate.** Validity dates need the wall clock, so a verifying connection is refused until SNTP has set it (`clock_is_set()`), with an error starting `"clock not set"` (`WIFI_TLS_ERR_CLOCK`); if SNTP had given up, the refusal restarts it, so a retry a few seconds later works.
- **Opt-out, per connection:** Lua `conn:setInsecure(true)` (HTTP, before `get`/`post`) or `tcp:setInsecure(true)` (before `connect`); native `http->setInsecure(c, true)` or `tcp->connectEx(host, port, PCTCP_TLS | PCTCP_TLS_INSECURE)`. Skips verification and the clock gate; logs `[TLS] <host>: certificate verification DISABLED`. For self-signed dev servers only.
- **TCP TLS sockets** report connected (`TCP_CB_CONNECT`, writable) only after the handshake (`MG_EV_TLS_HS`); the connect timeout covers the handshake.
- **CA bundle**: 11 roots chosen from the chains of `store.picodeck.net`, `github.com` and `*.githubusercontent.com`, parsed once at boot (`wifi_tls_init`, on the OS stack) into one chain every verifying connection shares. `tests/unit/test_ca_bundle.c` checks it parses whole and that captured chains verify against it. The root list (with the reason for each) and the add/refresh/check workflow are in `tools/gen_ca_bundle.py` (`ROOTS` and the docstring).
- **Randomness** (`rng.c`): RP2350 TRNG (von Neumann + CRNGT + autocorrelation health tests; software-reset after every use so pico_rand never meets a halted block) → mbedTLS entropy pool → one CTR_DRBG per core, seeded only at shallow points (Core 0 on the OS stack before `wifi_init`, Core 1 at the top of `core1_entry`); Core 1 draws come from a 512-byte pool that `wifi_poll` refills. Mongoose's `mg_random` (`MG_ENABLE_CUSTOM_RANDOM`) and `picocalc.crypto` use it; `MBEDTLS_ENTROPY_HARDWARE_ALT` (get_rand_64) is off. It fails closed: no seeded/working DRBG → `mg_random` returns false with zeros (no get_rand fallback), TLS is refused, Lua `crypto.randomBytes` raises and native `randomBytes` returns false with the buffer zeroed. The `stack` dev command reports `core1_peak` (Core 1 stack painted at boot) alongside `msp_peak`.

## HTTP client (`http.c`)
- Mongoose-based HTTP/1.1 client on Core 1; static pool of 8 connections (`HTTP_MAX_CONNECTIONS`). HTTPS via `pico_lwip_mbedtls` + `pico_mbedtls` (`src/mbedtls_config.h`), certificate-verified.
- `pending` bitmask set by Core 1 (`http_ev_fn`); Lua callbacks fired by Core 0 via `http_lua_fire_pending()`, which is never re-entered (a callback that sleeps or trips the hook leaves later events for the outer call). Native apps get no callbacks (`http_fire_c_pending` is a no-op) and poll `http->isComplete()`.
- The response is parsed in `http_ev_fn` (plain `mg_connect`, no Mongoose HTTP handler): Content-Length, chunked (decoded) and close-delimited bodies (COMPLETE on the server's close; bytes that did not fit the ring are spilled and stay readable), keep-alive reuse. A body cut short (reset, early close, OOM) is FAILED, never COMPLETE.
- A request (`get`/`post`) is accepted only in IDLE/DONE/FAILED; otherwise it returns false ("a request is already in progress"). POST bodies are binary-safe. The read timeout runs from the moment the request is sent (state HEADERS), not only once headers arrive.

## TCP sockets (`tcp.c`)
- Raw TCP/TLS client on Core 1; pool of 4 (`TCP_MAX_CONNECTIONS`); non-blocking, Core 0 requests, Core 1 handles.
- Lua callbacks (`setConnectCallback` / `setReadCallback` / `setCloseCallback`) get the socket and fire from `tcp_lua_fire_pending`; events without a callback stay for `getEvents()`. `setConnectTimeout` (next `connect`, default 15 s) and `setReadTimeout` (default off) reach the connection.
- Data left in Mongoose while the ring was full moves on every poll; buffered data stays readable after the peer closes. A failed `mg_send` fails the socket. Native `tcp->close` releases the slot (the handle is invalid afterwards).

## Audio (`audio.c`, `sound.c`, `wav.c`, `fileplayer.c`, `mod_player.c`, `mp3_player.c`)
- PWM output on GP26 (L) / GP27 (R). **One mixer** (`audio_mix.c`, which the simulator shares) sums every source per 44.1 kHz frame: the sample players (`sound.c`), the PCM stream ring (`audio_ring.h`: fileplayer, MOD, the native/Lua stream API) and the square-wave tone. It then clips and applies the master volume. `audio.c` is only the output: PWM fed by a DMA channel whose completion interrupt (DMA_IRQ_0, registered on Core 1 by `audio_stream_poll`) renders the next 128 frames with `audio_mix_render`. The output starts with the first sound (`audio_output_ensure_running`, silent buffers first) and runs, silent between sounds, until the app's teardown stops it (`audio_output_stop`). Starting or stopping the stream touches neither the output nor the other sources. `audio_apply_clock()` (in `launcher_apply_clock`) re-derives the PWM divider after a clock change such as the video player's 300 MHz boost. Each source has its own lock against the render: `sound.c`'s `s_mix_cs` for the sample players, `audio_mix.c`'s `s_src_cs` for both the stream (starting/stopping: the ring clear, the rate, `s_stream_on`) and the tone (all of its state) — striped spin locks, never nested, never held across SD, PSRAM copies, printf or umm. The MP3 player still drives the PWM slice with its own DMA and stops this output while it plays.
- All WAV loaders share one RIFF chunk walker (`wav.c`, host-tested + fuzzed): 8/16-bit PCM, 1-2 channels, EXTENSIBLE resolved; float, 24/32-bit, ADPCM and >2 channels are refused. Samples keep the first 64 KB of data; the fileplayer streams **16-bit only**.
- `sound.c`: 8 sample slots + 8 player slots, mixed by `sound_mixer_process()` inside `audio_mix_render` (from `audio.c`'s DMA refill ISR on Core 1). Anything that frees a sample or changes which sample a player reads takes the mixer lock (`s_mix_cs`, a striped critical section); `sound_sample_destroy()` stops and detaches every player still using the sample first. A player never owns its sample. In Lua a `sampleplayer` keeps its sample alive as a user value (`sampleplayer(path)` and `sample:play()` anchor a sample of their own; `getSample()` returns that object); collected players and samples give their slots back (a player also its callback slots); freed handles hold NULL and are rejected.
- `fileplayer.c`: streaming WAV from SD. Each fileplayer owns its file (and data-chunk fields); one plays at a time on the stream. Flow control: with F stream-ring frames free, a player at speed r reads at most floor(F·r) frames, so nothing is dropped and a WAV plays for its real length.
- `mod_player.c`: pocketmod, 128 frames per update, only when the ring has room.
- `mp3_player.c`: libmad; 32 KB PCM ring in PIO PSRAM; its own DMA ISR (DMA_IRQ_1) reads an 8 KB SRAM staging buffer, refilled by Core 1 with that ISR masked around the index updates. The decode loop continues only when a refill brought new data (SD busy / fed ring empty → next tick; EOF → loop back at most once per update, or finish). Stop/pause ramp to silence and wait for the ISR to play the ramp before the DMA stops.
- `mp3_player_update()`, `fileplayer_update()` and `mod_player_update()` run on Core 1 every 1 ms tick.
- `audiostat [reset]` (dev command): Core 1's tick cost (ticks, over 1 ms, missed, the longest) and the audio output's refill interrupt (count, time, the longest), stream and MP3 underruns, busy sample voices, `sys_khz`; `reset` starts a new window. `tests/e2e/test_audio_hw.py` measures with it.
- **Locks (Core 0 ↔ Core 1)**: each player has a mutex (`fileplayer.c` `s_lock`, `s_mod_mutex`, `s_mp3_mutex`) guarding its file / data / state. Core 0 takes it blocking, only for field updates (files are opened, closed and freed outside it, after detaching); Core 1's update only ever **try-locks** it and skips the tick. Core 1 never blocks on the SD card either: it reads with `sdcard_try_fread_at()` (seek + read under one try-lock, `SDCARD_BUSY` when Core 0 holds the card) and keeps its own file offset — Core 1 reads only through `sdcard_try_fread_at()`, never `sdcard_fseek`.
- Volume (master, MP3) scales the signed sample about PWM mid-scale; silence is always `PWM_MID`. Volumes are 0-100 everywhere (`audio.setVolume`, sampleplayer, fileplayer, mp3player, modplayer); larger values clamp to 100 (the mixers scale by vol/100).
- The simulator reuses `fileplayer.c`/`mod_player.c` but has its own copies of the sample mixer and MP3 player (`simulator/sim_audio.c`): keep them in step with `sound.c`/`mp3_player.c`.

## Video player (`video_player.cpp`)
- MJPEG with JPEGDEC (decoder state in static SRAM). Frame pool (3×96 KB JPEG buffers) in QMI PSRAM; Core 1 prefetches frame N+1 from SD while Core 0 decodes frame N.
- Frame + audio chunk indices sized from the AVI header (cap `VIDEO_MAX_FRAME_INDEX`); beyond the cap playback/seek fall back to sequential chunk scanning.
- Seeks clamp and never wrap; with loop off the last frame is held (`ended`). Built-in progress OSD drawn into the frame after decode. Hardware-only (the simulator stubs it).

## PIO PSRAM (`pio_psram.c`)
- Second 8 MB PSRAM on the mainboard, via PIO1 SPI; bus independent of QMI PSRAM/flash XIP. `pio_psram_init()` runs early in `main()`; non-fatal if the chip is absent.
- Layout (`pio_psram.h`): MP3 PCM ring `0x0000` (32 KB), a video region `0x8000` (256 KB) reserved for the OS but unused (the video frame pool lives in QMI PSRAM), apps from `PIO_PSRAM_APP_BASE` = `0x48000`.
- App access is limited to `[PIO_PSRAM_APP_BASE, chip end)` by `pio_psram_app_range_check` (64-bit, host-tested): Lua `sys.pioPsramRead/Write` raise on anything overlapping the OS region, negative, or past the chip; native `g_api.psram->pioRead/pioWrite/pioBulkRead/pioBulkWrite` (`src/main.c`) do nothing on a refused call (a read leaves `dst` untouched) and log `[NATIVE] psram->… refused`.
- DMA vs the XIP cache (`pio_psram_xip.h`): a source in cached QMI PSRAM (`0x11…`) has its lines cleaned (`xip_cache_clean_range`) and is read through the uncached alias; a cached destination gets whole lines DMA'd with `xip_cache_invalidate_range` before and after, and its partial end lines copied by the CPU from a bounce buffer (invalidate only lines the transfer owns entirely). Transfers hold the driver lock one 4 KB segment at a time and yield it to a waiting core between segments.

## Keyboard (`keyboard.c`, `kbd_event_queue.h`)
- The STM32 keyboard controller (I2C1, 10 kHz: 100 kHz locked it up after extended use) queues `[state, keycode]` items in a FIFO: state 1=pressed, 2=hold, 3=released; keycode is ASCII for printable keys (already shifted) or a `KEY_*` code. Released items are confirmed for buttons; **hardware-pending**: whether letters report a release, and which keycode a shifted symbol is released under (`!` vs `1`), until the device checklist in the Task 20 report runs.
- **Bus engine** (`kbd_i2c.c`; scheduling in the pure, host-tested `kbd_bus.c`): after `kbd_init()`'s probe, all STM32 traffic runs asynchronously on Core 0, driven by the I2C1 interrupt and default-alarm-pool alarms. That covers FIFO reads, the battery read (every 5 s; `kbd_get_battery_percent` returns the latest) and backlight writes (queued, latest wins, first in line). Nothing waits on the bus; the old blocking poll cost 107 ms/s of Core 0.
  - It reads the FIFO back to back while items come, then 10 ms after it reads empty. A due FIFO read goes before a due battery read (the battery follows at once). `kbdstat` `max_gap_us` is the time from an empty answer to the next read's result: ~16 ms (the 10 ms interval plus a ~6 ms read). A key pressed just after the STM32 answered empty also waits out the rest of that read, so the worst key-to-ring latency is ~22 ms; a backlight write (rare: dimming, the menu) goes first and can add ~3 ms.
  - Items wait in a 16-entry ring; `kbd_poll()` decodes up to 8 of them per poll (`KBD_POLL_MAX_ITEMS`), so one poll's events always fit the 16-entry event queue. A full ring stops the reads and the STM32 keeps the rest.
  - Engine steps run with interrupts disabled for a few µs; task-side calls touch its state under the same mask.
  - `kbd_discard_pending` is non-blocking: it empties the ring, and the engine drops items until a FIFO read begun after the call reads empty.
  - A failed transaction (NACK, timeout) stops the engine. The next `kbd_poll()` runs the ~12 ms bit-banged bus recovery in task context: at once for the first 10 failures in a row, then at most every 100 ms.
  - Clock changes pause it: `kbd_pause_bus` in `launcher_apply_clock`, resumed by `kbd_apply_clock`.
  - Deliberate resets (dev `reboot`/`reboot-flash`, the system menu, `sys.reboot`, OTA, the out-of-memory reboot) call `kbd_prepare_reset()` first, so a reset never cuts an STM32 transaction mid-byte (an interrupted transaction can lock the STM32's I2C slave until a power cycle). Resets nobody prepares:
    - HardFault: `hardfault_c` (either core) first calls `kbd_i2c_halt()`, a set-once flag (one store, safe from a fault handler) that stops the engine at its next job boundary; nothing resumes it. A Core 1 fault leaves Core 0 running the engine, which finishes the transaction in flight (~6 ms) and starts no other, long before the handler resets 3 s later. On a Core 0 fault the engine is frozen anyway (its interrupts cannot preempt HardFault), and the 3 s hold lets a transfer already queued in the I2C block finish.
    - Watchdog: FIFO and battery reads stop when `kbd_poll()` (or `kbd_poll_background`) has not run for 1 s (`KBD_BUS_UNPOLLED_US`, in `kbd_bus.c`); backlight writes still go, and the next poll reads the FIFO at once. A Core 0 stall that trips the watchdog (a native app that stops calling `sys->poll()`: ≥ 10 s) therefore finds the bus idle. Nothing is lost: the STM32 keeps the items, as with a full ring; a key pressed meanwhile reaches the app one poll later than it would have. The same happens at boot: the engine reads for a second after `kbd_init()` (the battery included), then waits for the launcher's first poll; the boot backlight writes (`kbd_set_backlight` after `kbd_init` and after `config_load`) still land.
    - Still exposed: a watchdog reset less than 1 s after the last poll that lands mid-transaction (the bus is busy ~37% of the time while polled), and brown-out or power loss.
  - USB storage mode stretches the idle interval to 500 ms (`kbd_set_poll_interval_ms`); items still come back to back, and the battery every 5 s.
  - It stays on Core 0, because `sys.pauseBackground` stops Core 1.
- Dev command `kbdstat` (`reset` zeroes, `fault` NACKs the next transaction) prints the engine's counters and `sys_khz`. `tests/e2e/test_kbd_hw.py` checks cadence, cost, recovery, a clock change, the stop while nobody polls and idle dimming on the device; its timing fixtures keep harness commands out of their windows (every dev command is answered inside the app, in a service pass that stalls it a few ms).
- Every item is decoded in order (`kbd_fifo_apply`, header-only, shared with the simulator and `tests/unit/test_kbd_event_queue.c`) into a 16-event queue (`pollEvent`; oldest dropped), a key-down set (`isKeyDown`: reliable for buttons; letters (case-folded because Shift may come up first) and shifted symbols pending hardware confirmation; a key stuck down is cleared by `clearState()`/`kbd_clear_state`), a 4-char `getChar` backlog (still one char per poll) and the button masks. A press+release inside one poll reads as held for that poll.
- HOLD is a repeat of a press already seen (repeat-flagged events and a char, no press edge). A HOLD for a key pressed before `kbd_clear_state`/`kbd_discard_pending` only marks it held and "unseen": every later HOLD of it stays quiet until it is released and pressed again, so it cannot answer `ui_confirm` even if the STM32 repeats HOLD.
- `kbd_clear_state` also clears the queue; `lua_bridge_input_init` flushes it, so an app never receives the launcher's keys. Injected buttons/chars feed the queue too; in the simulator `hal_input.c` stages events and `kbd_poll` moves them in, so apps see them only after `input.update()`, as on hardware. On the device an injected key still down at `kbd_clear_state` (an active one-shot such as the injected Enter that opened the modal, or a `keydown` latch) stays held with no press edge and releases on retire/`keyup`; a still-pending injection is published with its edge by the next poll; an unread injected char is dropped (`kbd_inject_*` in `kbd_event_queue.h`, host-tested).
