# Simulator (`simulator/`)

`make simulator` builds `build_sim/picodeck_simulator` (SDL2 + Unicorn Engine for native ELF apps). The root `CLAUDE.md` lists the divergences that matter when trusting a simulator result; this file has the rest, plus the test control channel.

## Divergences from hardware
- `picocalc.crypto` is **absent** (Lua and native) — mbedTLS is firmware-only (`simulator/CMakeLists.txt` excludes `lua_bridge_crypto.c`; native crypto trampolines are stubs except `randomBytes`).
- TLS certificate verification, the SNTP clock gate and the TRNG are firmware-only: the libcurl transport keeps its own TLS policy and only stores the `setInsecure` flag. The OTA *checks* (checksum + signature against the TEST key, `src/os/ota_verify.c`) do run; flashing does not.
- `picocalc.video` is stubbed (no decoder): `player()` returns nil-backed handles; every video trampoline is a no-op.
- Display: the simulator has its own implementation (`stubs/driver_stubs.c`, host byte order, sharing the rasterisers in `src/drivers/display_clip.h`). Post-effects (`effectInvert`…`effectPosterize`) are no-ops on the native (Unicorn) path; Lua-side effects work. The native trampolines for `flushRows`/`flushRegion` copy the emulated framebuffer and present the whole buffer with a swap, so the OS overlay (toast, Show FPS) is drawn there as for `flush()` and each call counts as one frame (the firmware counts a `flushRows` sweep as one); Lua partial flushes run the firmware's overlay logic. A counter or toast the overlay pushes outside a partial flush's rows lives only in the GRAM analog, so the harness screenshot (`screenshot`, `get_pixel`: the presented image) shows it, but a firmware screenshot (`screenshot_save`, which reads the framebuffer) of a `flushRows`/`flushRegion` app does not. Hardware vertical scroll (`setScrollArea`/`setScrollOffset`/`getScrollOffset`) is emulated: flushes land in a GRAM analog and presents/screenshots are composed through the scroll registers, mirroring the ST7365P ring for the visible 320 lines (the chip's extra 160 frame-memory lines are not modelled).
- Game controllers: `hal/hal_pad.c` opens the host's SDL game controllers (hotplug; up to 4, ORed) as the `PAD_SOURCE_HOST` pad source (`src/drivers/pad_source.h`), published on Core 0 from the keyboard stub's SDL event pump; the stub ORs the sources into `kbd_get_pad*` and raises the menu on Home as `keyboard.c` does. Off under `--test-mode` (unless `--gamepad`) and with `--no-gamepad`; compiled out of the web build (`__EMSCRIPTEN__`: no `SDL_INIT_GAMECONTROLLER`, so the web demo is unchanged).
- Bluetooth gamepads: `sim_bt.c` implements `src/drivers/bt_pad.h` over a scripted radio, not BTstack. `bt sim add <addr> <cod hex> <name>` puts a device in pairing mode in range (`bt sim clear`), and the controller comes up (300 ms), a search ends (1.5 s) and a connection opens (0.5 s; fails for an address neither in range nor paired) on the simulator's clock, advanced whenever a `bt_pad_*` call runs; `bt sim press <buttons|none>` is the connected pad's report (`PAD_SOURCE_BT`), `bt sim drop` its link loss, `bt sim wake <addr>` a paired pad reconnecting. What is real: the Settings → Bluetooth page, the `bt_enabled` setting, the bonding store and `/system/bluetooth.dat`, the `bt` dev command and the pad source. Its notices also go to the test log (`[BT] ...`, `sim_log_os`). Unavailable in the web build (`__EMSCRIPTEN__`: no Settings item).
- Boot mirrors `src/main.c`: `config_load()`, idle-dim init, network, `bt_pad_init()`, Core 1, `system_menu_init()`, launcher. Idle dim stays inert (the keyboard stub never polls it).
- The launcher caches the app list at boot, but the `launch_app` RPC rescans `/apps` once when a name is not found, so newly staged apps launch without a restart; `rescan_apps` forces a rescan (e.g. after editing an existing app's `app.json`). Hidden apps (`/apps/.test`, `/apps/.dev`: `src/os/CLAUDE.md`) need neither: the same `launcher_launch_by_name` finds them fresh, and `sdcard_list_dir` lists those two dot directories (it still hides other dot entries) as firmware does.
- The SD HAL models the open-file COUNT of FatFS's `FF_FS_LOCK = 16` only: a 17th concurrently open file is refused (`[SIM] too many open files`). FatFS's per-file sharing rules (a file open for writing cannot be opened again) are not modelled. SD paths resolve `..` lexically and anything that would leave the SD root is refused (`[SIM] SD escape: <path>` on the `err` log source).
- Audio: the firmware's mixer and players run here unchanged (`audio_mix.c`, `sound.c`, `mp3_player.c`, `fileplayer.c`, `mod_player.c`). `sim_audio.c` is only the output: on the Core 1 thread it renders the mix at 44.1 kHz by wall clock (standing in for the DMA refill ISR) and queues it to SDL, skipping the SDL push once SDL holds 200 ms (the render still runs, so sources advance). Ring flow control, sample timing and callbacks, MP3 underruns and fades behave as on hardware; timing costs do not (`tests/e2e/test_audio_hw.py` measures them on the device).
- Networking: `make simulator` replaces `wifi.c`/`http.c`/`tcp.c` with its own libcurl/POSIX layer (`sim_wifi.c`, `sim_http.c`, `sim_tcp.c`: always online, none of the firmware's Core 0/Core 1 races). See the firmware-net build below for the real stack.
- `fs.seek` past the end of a file: the device (FatFS `f_lseek`) grows the file at seek time, leaving undefined data in the gap; the simulator's stdio seek neither clamps a read handle nor extends before a write, so `tell()` after such a seek can differ.
- Everything else (zip including read-in-place archive handles, modplayer, display clip rect, drawPlane, tilemap, sprites) mirrors firmware, including `g_api.version`.
- **Lua service hook**: the simulator (and the web build) service the Lua VM from the synchronous adaptive count hook; firmware runs the VM hook-free and arms the hook from a 1 ms Core 0 timer (`src/os/CLAUDE.md`, Service hook). Exit/menu/dev-command latency is covered on both by `tests/e2e/test_lua_hook_target.py`; VM speed and the watchdog only on hardware (`test_lua_hook_hw.py`).
- **SD card size and directory order**: `fs.diskInfo` reports the host filesystem's size and free space, capped at 32 GB (Lua integers are 32-bit; a multi-terabyte btrfs or XFS volume wrapped `total` negative). Directory listings come back in the host's `readdir` order (tmpfs newest first, ext4 hashed, btrfs by creation), unlike a FAT volume: the launcher's `MAX_APPS` cap keeps the first apps listed, so tests build cards that never exceed it (`tests/e2e/README.md`, App cap).

## Test control channel (`sim_socket_handler.c`, `sim_test_control.c`)
- `get_log_buffer {since_seq, tail}` returns `{lines:[{seq,t_ms,src,text}], next_seq, dropped, more}` with `src` = `lua`/`native`/`os`/`err`; `subscribe {"logs":true}` pushes `log {seq,src,text}` notifications.
- `app.exited` carries `{name, id, found, result: returned|error|exit_sentinel|load_failed, error, runtime_ms, launch_id}`; `launch_app` returns `{queued, busy, launch_id}` and `get_last_outcome` returns the last `app.exited` params (backfill when a notification was dropped). `get_running_app` always returns `{running, name|null}`.
- `display_stats.present_count`; `inject_*` return `input_seq` and `get_input_state` reports `consumed_seq`.
- `get_mp3_stats` returns the MP3 player's counts since boot: `underruns` (output frames with no MP3 data), `low_frames`/`idle_frames`/`overran`/`frame_us` (when the decoder decoded: `src/drivers/mp3_sched.h`), `decode_ahead`, and Core 0's pacing `idle_windows`/`idle_ms`. Compare before/after a run.
- `set_battery {percent, charging}` sets what `kbd_get_battery_percent` / `kbd_is_charging` report (default 100, false). `set_wifi_state {"status": "connecting"|"failed"}` pins the status `wifi_get_status` reports (network access unchanged) until the next `set_wifi_state`; `disconnected`/`not_available` make WiFi unavailable, `connected`/`online` restore the real state.
- The `dev_command` RPC (`{"cmd": "unzip ..."}`) is queued for Core 0 and served by the launcher loop, a Lua app's hook / `sys.sleep`, or a native app's `sys->poll()` (so a native app that never polls times the RPC out, as on firmware); it runs `ping`/`exit`/`unzip`/`rm`/`mv`/`pad`/`bt`/`audiostat [reset]` through the firmware handlers (`src/dev_ops.c`), and `list` / `list all` through `launcher_list_apps` (the lines go to the log buffer, source `os`; the reply is just `Listed apps`); `hw_target.SimTarget.command()` wraps it. `pad` drives the test gamepad source (`PicodeckSimulator.pad`, `Target.pad`); the E2E tests use it instead of a controller. The simulator's `audiostat` times its own Core 1 thread (5 ms ticks, `missed` always 0; `main.c`) and its render passes (`sim_audio.c`) in place of the refill interrupt, and reports `sys_khz=125000`; the stream fields are the firmware mixer's.
- `set_sd_busy {ms, after_reads}`: once `after_reads` (default 0) more of Core 1's `sdcard_try_fread_at` calls have gone through, they return `SDCARD_BUSY` for `ms`, as if Core 0 held the card (the simulator has no cross-core SD mutex, and its SD reads take no time). The fileplayer tests stall the stream with it (`tests/e2e/test_fileplayer.py`).
- The TCP listener binds 127.0.0.1 only; `--unix-socket PATH|none` overrides or disables the `./picodeck_control` UNIX socket (the E2E harness passes `none`). Python client: `tests/e2e/picodeck_simulator.py`.

## `--test-mode`
- Lua error screens and launch refusals return at once (the text is on the `err` source).
- Determinism: `math.random` is seeded with a constant at every app start (`lua_bridge.c`, `#ifdef PICODECK_SIMULATOR`), Lua's string hash seed is constant (so `pairs()` order over string keys repeats; `sim_lua_seed.h`), and the clock is pinned to 2026-01-01T00:00:00Z at boot (`getClock` reports `synced=true`; it then runs with the sim clock).
- **Virtual time** (`--virtual-time`, needs `--test-mode`; `PicodeckSimulator(virtual_time=True)`; `PICODECK_SIM_VIRTUAL_TIME=1` for every test-mode sim): the clock the OS and apps read (`getTimeMs`, `to_ms_since_boot`, the input hold, animators) is virtual. Only Core 0 (the main thread) moves it: `sleep_ms(n)` advances it by `n` and waits `n / multiplier` real ms (default 50x, so `sys.sleep(5000)` costs ~100 ms and reads back exactly 5000); a stretch of more than 50 ms without a sleep advances it at `min(multiplier, 1)` x real time; `set_time_multiplier 0` pauses it and `step_time {ms}` (returns `{now_ms}`) moves it, a paused `sys.sleep` returning only as it is stepped. Core 1, the socket thread, audio (SDL, wall-clock ring drain) and sockets stay real-time, so network timeouts measured in virtual time would fire early: it is opt-in per test and the audio/network suites stay on the wall clock. Without it the multiplier only scales `hal_sleep_ms`.

## Allocators
- Default `umm_*` is a counting allocator over host malloc: `umm_free_heap_size()` / `get_heap_info` report 8 MB minus the live umm/Lua bytes, but the largest free block is approximated by the free total and fragmentation is always 0. ASan builds poison free small-pool slots and the slack past each request, so overflows inside a slab are still caught.
- `--real-umm` runs `umm_*` on the firmware's own `umm_malloc` (device heap size, 200-byte blocks), so block waste, fragmentation and the largest free block behave as on hardware (ASan no longer sees inside the heap). On the 64-bit host Lua objects are about twice their device size, so the small-object pool classes double too (up to 256 B).

## Other builds
- Sanitizers: `make simulator-asan` (ASan+UBSan, `build_sim_asan/`) and `make simulator-tsan` (`build_sim_tsan/`), built with clang. Run the E2E suite against one with `PICODECK_SIM_BINARY=build_sim_asan/picodeck_simulator`; `asan_only` tests run only there. TSan is informational (the RPC socket thread and Core 1 audio state race by design).
- Firmware network stack: `make simulator-net` (`-DSIM_FIRMWARE_NET=ON`, `build_sim_net/`; also `simulator-net-asan`/`simulator-net-tsan`) compiles the firmware's own `wifi.c`, `http.c`, `tcp.c` on the vendored Mongoose as `MG_ARCH_UNIX` (BSD sockets, **no TLS**: HTTPS and `tls://` are refused), Core 0 = main thread, Core 1 = the sim's Core 1 thread. Host shims are in `net/` (spinlocks → pthread mutexes with the SDK's claimable ids 24-31; `get_core_num`; host randomness for `rng.h`/`mg_random`; `core1_calloc` → calloc; a stand-in Wi-Fi interface that joins `SimulatorWiFi` as 127.0.0.1 at boot; SNTP and the connectivity check stay on loopback). The firmware files only gain `PICODECK_SIM_FIRMWARE_NET` guards (the TLS section and the `time()` override in `wifi.c`) and `#ifndef` defaults (`WIFI_SNTP_URL`, `WIFI_CHECK_URL`, `PSRAM_UNCACHED_OFFSET`); their firmware objects are unchanged. `--build-info` prints `firmware_net=1`; `tests/e2e/test_network_firmware.py` (local servers in `tests/e2e/net_servers.py`) runs only against that build.

## Web (WASM) build

The browser demo at picodeck.net/try is built and released by [PicoDeck/web-sim](https://github.com/PicoDeck/web-sim) from this simulator's source (at PicoDeck's latest release that has the seam below); nothing here builds it. It runs Lua apps only: no Unicorn (no JIT in WASM), no networking, no RPC socket (`sim_test_control.c` is still compiled), no threads. Core 1 is `sim_core1_service()` (`main.c`, one tick), which web-sim's `web_core1_tick()` runs cooperatively every 5 ms from the core's wait points (`-sASYNCIFY` + `emscripten_sleep`); the desktop Core 1 thread runs the same function, so a new Core 1 duty goes in `sim_core1_service()`. WebAssembly traps on function-signature mismatches that x86 and ARM tolerate, so a new `http_*`/`tcp_*` function in `src/drivers/`, or a changed signature, needs a matching stub in web-sim's `platform/web_net_stubs.c`: web-sim's nightly build against develop reports the break in web-sim's own Actions. To check a core change against the browser locally, clone web-sim next to this checkout and run `make build test` there; its `PICODECK` defaults to `../picodeck`, or pass `PICODECK=<this checkout>`.

### Web build seam

The web build is split so a separate project, [PicoDeck/web-sim](https://github.com/PicoDeck/web-sim), can own everything web-facing. `hal/web_platform.h` states the whole contract:

- **The core provides (stays here):** `sim_core1_service()` (one Core 1 tick, no sleep), and the core functions the web sources may call, `hal_input_inject_char()` (`hal/hal_input.h`) and `hal_display_get_framebuffer()` (`hal/hal_display.h`). The `__EMSCRIPTEN__` hooks in `main.c`, `hal/hal_display.c`, `hal/hal_timing.c`, `stubs/keyboard_stub.c` and `stubs/pico_sdk_stubs.h` call the web sources' side; the Emscripten facts in `CMakeLists.txt` (SDL from Emscripten's ports, no threads, curl or Unicorn, `SIM_SIZEOF_LONG 4`) stay here too.
- **The web sources define:** the four functions in `hal/web_platform.h` (`web_core1_tick`, which paces `sim_core1_service()` and calls nothing else of Core 1's; `web_yield`; `web_yield_if_due`; `web_fs_init`), and the desktop-only hooks the core calls, since the browser has no RPC socket, terminal tracking or Unicorn: `sim_socket_notify`, `sim_socket_notify_log_subscribers`, `sim_set_active_terminal`, `sim_get_active_terminal` and `unicorn_run_app`.
- **The web project's build:** the directory `PICODECK_WEB_DIR` names (a PicoDeck/web-sim checkout; required) holds `web.cmake`, which `CMakeLists.txt` includes in an Emscripten build. It must set `PICODECK_WEB_PLATFORM_SOURCES` (the definitions above) and `PICODECK_WEB_NET_SOURCES` (stubs every `http_*`/`tcp_*` the core calls), both absolute paths, and define `picodeck_web_package(target)`, called once the simulator target exists, which builds the SD image and sets the link options and page. It can use `PICODECK_ROOT`, `PICODECK_WEB_DIR` and `CMAKE_BINARY_DIR`.

A change to the hooks, to `sim_core1_service()`'s role or to `hal/web_platform.h` is a change to this contract: say so in the commit, since web-sim builds against PicoDeck's releases.
